Manual testing — the whole map on one page

Start at the top of the tree and walk down: how much of the internals you can see, what size of thing you are testing, whether you check what it does or how well it does it, and finally which technique tells you which test cases to write. Every box below is clickable — it jumps to its explanation.

1How much you can see inside

The first fork in the tree. It decides when you can write the test and what it survives.

Black box spec-based

Test from the outside, using only the specification. You never look at the code, so the test still works after the code is rewritten — as long as the required behaviour did not change.

Tiny exampleDeposit 0 USD → expect “amount must be greater than 0”.

White box structure-based

Test from the inside, using the code. You can only write these after the thing has been designed or written, and they break when the code is restructured.

Tiny examplePick inputs so both sides of if (balance > 0) run at least once.

Grey box mixed

You drive it from the outside, but you know some internals — the DB schema, the API contract, the log format — and you use that knowledge to check the result. This is what most QA work in this team looks like.

Tiny exampleSave a group in Admin, then check the row landed in the database.

Manual vs automation who runs it

Same techniques, different runner. A person exploring finds surprises a script never will; a script repeats 500 checks overnight without getting bored. Design the test first, then decide who runs it.

Rule of thumbNew and unclear → manual. Stable and repeated → automate.
◆Experience-based testing is a third family alongside black and white box: it leans on the tester’s knowledge instead of a document or the code. See section 7.

2Test levels — how big is the thing under test

Same product, four zoom levels. Each level finds a different kind of defect, so skipping one leaves a gap.

Unit / component smallest

One function or class, on its own, with everything around it faked. Fast, precise, and it points straight at the broken line. ISTQB calls this component testing.

Tiny exampleThe swap formula returns 35, not 3.5, for “35 %” at price precision 3.

Integration the seams

Two or more parts talking to each other. Every part can be correct on its own and the pair still wrong — mismatched units, swapped fields, a format nobody agreed on.

Tiny exampleMCP → connector → PLAT: does the value survive all three hops unchanged?

System whole product

The complete system end to end, in an environment close to production, doing what a real user would do. This is where most manual testing happens.

Tiny exampleOpen a position in the Manager and see it arrive in the LP session.

Acceptance the customer

Not in the diagram, but it is the level above system: does this actually solve the business problem? Run by or with the people who asked for it.

Tiny exampleA user completes a full day of routine work on the new screen.

3Integration — the order you plug things in

Only relevant at the integration level. It is a choice about how fast you go versus how easily you can tell what broke.

Incremental one at a time

Add one part, test, add the next. Slower to set up, but when something fails you already know it was the piece you just added.

Tiny exampleAdd the router, test. Add the quoter, test. Add the config service, test.

Top-down needs stubs

Start at the top layer and fake everything underneath. You see the user-facing flow early, but the fakes (stubs) cost time to write.

Tiny exampleTest the Admin screen against a fake API that always returns 3 groups.

Bottom-up needs drivers

Start at the lowest layer and fake the callers. The engine gets solid early, but nobody sees a working screen until late.

Tiny exampleDrive the connector with a script instead of the real UI.

Non-incremental (“big bang”) all at once

Wire everything together, then start testing. Cheap to set up and tempting under deadline — but a failure could be anywhere, so debugging is slow.

Tiny exampleDeploy all services, click one flow, get an error with no idea which hop failed.

4Functional vs non-functional

Functional asks “does it do the right thing?”. Non-functional asks “is it good enough?” — and it has its own quality attributes.

Functional what it does

Behaviour against the rules: correct results, correct rejections, correct messages. This is where the design techniques in sections 6–8 are used.

Tiny exampleA limit order fills the moment the price touches the limit — not before.

Non-functional how well

Everything the feature must also be: fast, stable, usable, portable, secure. Same feature, different question — and usually a different kind of defect.

Tiny exampleThe same order fills in under 200 ms with 500 users online.

Usability can they use it

Can a real user reach their goal without being told how? Measured by observing people, not by reading the screen yourself.

Tiny exampleA new user finds the setting in under a minute, unaided.

Compatibility elsewhere

Does it still behave in other browsers, clients, versions or operating systems? Combinations explode fast — this is the classic home of pairwise testing.

Tiny exampleSame MCP answer in Claude Desktop, Claude Code and Onyx.

5Performance types — four different questions

They are not intensities of the same test. Each one answers a question the others cannot.

Load expected

Realistic, anticipated load from a controlled number of users, rising towards the target. Question: can it cope with the traffic we actually expect?

Shaperamp up → hold → ramp down
Tiny example500 users, one query each per minute.

Stress past the limit

Peak load at and beyond the specified limit, or normal load with resources taken away. Question: how does it fail, and does it recover?

Shapepush past the maximum
Tiny exampleGo to 2 000 users; then halve the container memory.

Scalability tomorrow

Ability to meet future requirements that exceed today’s. Question: how far can we grow before we breach the current targets? Once you know the ceiling, you can alarm on it in production.

Tiny exampleStill under 1 s with 3× today’s accounts?

Stability / endurance over time

Steady load held for an operationally realistic period. Question: do resources leak — memory, DB connections, thread pools — and degrade it hours later?

Tiny example8 hours of steady load; memory flat at the end, not climbing.
◆Also in the family: spike (sudden burst, then back to normal) · concurrency (many users doing the same thing at the same instant) · capacity (how many users/transactions before the targets break).
throughput = virtual users ÷ (processing time + think time) Which is why “500 users” is not a load. The same 500 users querying once a minute = 30 000 queries/h; once an hour = 500 queries/h. Sixty times the difference.

6Black-box techniques — how to pick the test cases

You cannot test everything. These tell you which few tests carry the most information, and they give you a number for “how much did we cover”.

Equivalence partitioning start here

Split each input into groups the system should treat identically, then test one value per group — the invalid groups too. Groups must not overlap and must not be empty.

Tiny exampleVolume: < 0 | 0 | 0.01–100 | > 100 → 4 tests, not 400.

Boundary value analysis the edges

Mistakes cluster at the edges of those groups. Test the boundary and its neighbour (2-value), or the boundary and both neighbours (3-value, stricter). Only works on ordered groups.

Tiny exampleLedger limit 92 days → try 91, 92, 93.

Decision table combined rules

For business rules where several conditions combine. One column per rule; test every feasible column. It also exposes rules the spec forgot to state.

Tiny exampleretail? × margin ok? × market open? → fill / reject / queue.

State transition has states

For anything with a lifecycle. Test every valid transition (the usual target), and attempt the invalid ones — one invalid per test case, so one defect cannot hide another.

Tiny examplePending → Filled ✓ · Pending → Cancelled ✓ · Filled → Cancelled ✗ (attempt it).

Pairwise too many combos

When full combinations are impossible, cover every pair of values instead. Small set, surprisingly strong: most failures come from one or two variables interacting.

Tiny example4 clients × 3 languages × 3 roles = 36 → about 12 tests.

Classification tree draw it first

Draw the parameters and their values as a tree before choosing combinations. It does not produce test cases by itself — it feeds partitioning, boundary analysis or pairwise.

Tiny exampleclient · browser · language · OS → then pick the pairs from the picture.

Use case testing real flows

One test for the main path, plus enough tests to cover every alternative path and every error path. Closest to how the product is really used — and good raw material for performance profiles.

Tiny examplePlace order → main path; no margin, market closed, LP down → 3 more.

Combine them usually best

They are not rivals. A decision table tells you which combinations matter; partitioning tells you which value to use inside each condition.

Tiny exampleDecision table row “margin ok = false” → pick a boundary value for it.
◆Empirical backing for pairwise: in a medical-device study, 66 % of failures came from a single variable, and single- plus two-variable interactions accounted for 97 %. The residual risk is failures needing three or more variables at once.

7Experience-based — where the techniques run out

No formal coverage number here. These find the defects a systematic technique walks straight past, and they work when documentation is thin or time is short.

Error guessing go for the throat

Attack the places defects usually hide, based on what has broken before in this team and this product.

Tiny exampleempty list · 0 · null · a name with a trailing space · a date at midnight.

Exploratory timeboxed

A session with a charter (a goal) and a clock. You design, run and learn at the same time, and the next test comes from what the last one told you.

Tiny example“60 min: try to break the ledger date filter.” Notes as you go.

Checklist-based memory aid

A list of things worth remembering, not step-by-step scripts. Keeps coverage broad without freezing the tester into a fixed path.

Tiny example“Every list: empty, one row, 500 rows, sorted, filtered, exported.”

8White-box coverage — the two you will meet

Mostly a developer’s tool, but the numbers land in your reports, so it pays to read them correctly.

Statement coverage weaker

Every executable line runs at least once. If a line holds the defect, at least it got executed — which gives it a chance to fail visibly.

Tiny exampleAn if with no else: one test can already reach 100 %.

Branch coverage stronger

Every decision is taken both ways — true and false. Full branch coverage implies full statement coverage; the reverse is not true.

Tiny exampleSame if: now you need the skipped path too.

Reading any coverage number

Every technique in this page defines its own coverage items — partitions, boundaries, table columns, transitions, statements, branches. The percentage always means the same thing.

coverage % = items exercised ÷ items total × 100

9How to choose — the short version

There is no single best technique. The syllabus is blunt about it, and so is practice.

SituationReach forWhy
A field with rangesEquivalence partitioning + boundary valuesCheapest tests that still find the classic off-by-one.
Rules with several conditionsDecision tableExposes combinations — and gaps in the spec.
Anything with a lifecycleState transitionInvalid transitions are where the silent bugs live.
Too many configurationsPairwise (+ classification tree)Shrinks the set without losing most of the risk.
Whole user journeysUse case testingMatches how it is really used; reusable for load profiles.
Thin or missing specExploratory + error guessingWorks with no documentation at all.
A release you must not breakAll of the above, combinedSystematic gives breadth, experience gives depth.
◆Two things worth memorising. First: 100 % coverage does not mean “fully tested” — it only means that model has no more tests to give you. Second: black-box and experience-based techniques are strongest together, because the second one covers the systematic blind spots of the first.
◆What drives the choice (per ISTQB): the type of project · the schedule · the information available · the testers’ skills.

Testing AI — the same craft, different ground rules

Everything on the manual-testing page still applies: an AI product is mostly ordinary software with one probabilistic part in the middle. What changes is that part. You often cannot say what the correct answer is, the same input need not give the same output twice, and the behaviour can drift after release. So the unit of testing moves — from “a function” to the data and the model — and a single passed test stops meaning anything on its own. Every box below is clickable.

Grounded in ISTQB CT-AI v2.0 (Certified Tester AI Testing, GA 2026-04-17) and ISTQB CT-GenAI v1.0 (Testing with Generative AI, 2025-07-25). Sections 1–7 are about testing a system that contains AI; section 8 is the other direction — using GenAI to do your testing.

1Why AI breaks normal testing

Four properties do all the damage. Everything else on this page is a response to one of them.

No test oracle the core problem

In normal testing you know the expected result, so passed/failed is obvious. With AI the expected result is often unknown, subjective, or beyond what a human can check — there is no agreed ground truth. Vague requirements make it worse.

Tiny example“Is this the best product recommendation?” has no right answer to compare against.

Non-determinism it varies

Probabilistic sampling, floating-point limits and GPU parallelism mean the same input can give a different output. One failed run proves nothing; one passed run proves even less.

Tiny exampleThe model calls a cat a dog once in 200 runs — a single test will never tell you that.

Locked vs adaptive does it change?

Locked — behaviour fixed after deployment (most deployed models). Largely deterministic, so expected results stay valid; an updated model counts as a new system and is retested. Adaptive — keeps learning in production (e.g. reinforcement learning), so its behaviour can change during the test. Most LLM products sit between: locked at runtime, updated periodically.

Rule of thumbAdaptive → you cannot pre-write tests for behaviour that does not exist yet. Build an automated core suite and re-run it on every change.

Statistics, not verdicts consequence

Because of the three above, results are measured over a large, representative sample and reported as a rate with a confidence level — not as one verdict. The test suite has to be big enough to be statistically significant.

Tiny example“98 % accuracy, ±1 % at 95 % confidence” — not “the test passed”.
◆Ways round the oracle problem: define acceptable ranges and tolerances instead of exact values · pin the environment so runs are repeatable · ask a domain expert (fallible, but a baseline) · use metamorphic testing — check relations between outputs, not the outputs · use a pseudo-oracle, a second independent implementation (see section 5).

2Quality characteristics — what you are allowed to demand

ISO/IEC 25059 extends the familiar 25010 model with characteristics that only make sense for AI. They are what your acceptance criteria get written against.

AI functional correctness adjusted

Perfect accuracy is not achievable, so correctness is defined with an accepted error rate: both correct and incorrect outputs count, and a threshold says how many wrong answers are tolerable.

Tiny example“≥ 98 % of classifications correct” replaces “all classifications correct”.

AI robustness under pressure

Holding that level of correctness anyway — with biased, adversarial or invalid input, external interference, adverse conditions, or an operator misusing it.

Tiny exampleAccuracy must not collapse when the photo is blurred or the prompt is hostile.

Functional adaptability self-adjusting

Can the system adapt on its own to a changed operating environment after deployment — and does it do so correctly?

Tiny exampleA drone switches flight mode when it crosses a set altitude.

User controllability & intervenability the off switch

A human (or another agent) can step in in time — controllability is the general ability to intervene, intervenability is intervening specifically to prevent harm or hazard.

Tiny exampleManual override is offered the moment performance degrades by 30 %; full deactivation past 50 %.

Transparency can you explain it

The right information about the system reaches the people who need it: model version, data provenance, documentation, limits. Testable through reviews and through an API that reports it.

Tiny exampleAn endpoint returns the deployed model’s version id and a link to its documentation.

Societal & ethical risk mitigation the broad one

Accountability, fairness and non-discrimination, privacy, safety and security, human control of technology, human-centred design, respect for the rule of law, environmental sustainability, labour practices.

Tiny exampleEqual approval rates across protected groups — tested in section 4.
◆Acceptance criteria for AI are statistical, probabilistic or threshold-based, not binary. Write them that way before you start, or you will have no way to call a result passed.
◆Safety makes all of this harder: requirements start as vague goals encoded in training data, so traceability is poor · non-determinism prevents guarantees · self-learning drifts away from what you tested · decisions are hard to explain (LIME and similar help, at a cost to performance) · functional-safety standards have not caught up, while the EU AI Act already classes AI used as a safety component as high-risk.

3Test levels — two new ones on top of the usual four

Component, integration, system and acceptance all still happen. An ML system adds two levels that have no equivalent in conventional software.

Input data testing new

The data is the specification, so it gets its own level — training, validation and test datasets, plus the production data the model uses to generate predictions in operation. Section 4.

Tiny exampleHalf the training rows for one account type are missing — found here, or never.

ML model testing new

The trained model as the thing under test — the ultimate output of the ML workflow, before it is wired into anything. Section 5.

Tiny exampleMeasure accuracy, recall and robustness on a held-out set.

The conventional four, unchanged

Component — the non-AI parts, such as data capture and communication. Component integration — the model actually receives the input and its prediction reaches the rest of the system; API testing lives here when AI comes as a service. System — model performance survives being embedded, which matters especially after the model was deliberately changed (e.g. a compressed DNN), plus non-functional work such as time to deliver a prediction. Acceptance — is the service suitable for the intended system, and were the ML performance criteria met.

Watch outA model that is excellent standing alone can be mediocre once compressed and deployed. That is a system-level finding.

Risk-based, by workflow stage

Most regulatory frameworks require a risk-based approach. One usable split: development risks (sub-optimal algorithm, poor evaluation approach, framework vulnerabilities — §7) · data risks (biased, unrepresentative, broken pipeline — §4) · model risks (below target performance, overfitted, susceptible to adversarial examples — §5).

AlternativeCategorise the risks by the ISO/IEC 25059 characteristics from section 2 instead.

4Input data testing — the dataset is the spec

Most defects blamed on “the model” were already in the data. Five kinds of check, all of which you can run before a single prediction is made.

Testing for bias fairness

Non-random, unfair differences in treatment based on sensitive attributes — gender, age, race — which is often unlawful. Two sources: data bias (unrepresentative or poisoned training data) and algorithmic bias (a threshold or rule that produces unfairness even on clean data).

Approaches: review how the data was collected and annotated and which populations it represents · exploratory data analysis looking for skewed distributions and odd groupings across sensitive attributes · run a representative dataset through the system and look for statistically significant differences in outcome between groups — which catches bias whether it came from the data or the model.

Disparate impact analysisPick the sensitive attribute → build counterfactuals (same loan application, gender flipped) → run them → analyse enough of them for a statistically significant result. Works on combinations of attributes too. Keep the counterfactuals realistic, or you measure the model’s reaction to nonsense instead of its bias.

Data pipeline testing layered

Start with a design review. Component: ingestion, transformation scripts, sensor interfaces — code review, static analysis, validation rules, error handling, and vulnerabilities that would let malware or poisoned data in. Component integration: data flows across internal interfaces and is interpreted correctly on the far side. System: smoke first, then functional (transformations, routing), then non-functional (load, scalability, security), plus fault injection with defective inputs. System integration: sources, storage, monitoring and the model downstream.

Tiny exampleBack-to-back the operational pipeline against the training pipeline — the classic training/serving skew bug.

Data representativeness does it match reality

How closely training, validation and test data match what the model will actually meet in operation. Catches skewed datasets, missing data, disproportionate feature distributions, operational scenarios with no coverage, and imbalanced classes.

Define the target population first — domain experts, data from existing or similar systems, benchmark datasets from trusted sources — then analyse your dataset’s characteristics against it.

Tiny exampleThe model will serve 40 % mobile users; the training set is 98 % desktop.

Dataset constraint testing schema for data

Write the rules the data must satisfy, like a database schema, then check them. Single-value constraints apply to one attribute in one instance (type, range, format). Multi-value constraints apply across instances — a total that must stay within bounds, a cap on duplicates, a limit on how many nulls are allowed (often zero).

Tiny examplePoints awarded across one race must exceed 50.5 and not exceed 102 — no single row can tell you that.

Label correctness testing supervised only

Wrong labels directly undermine performance and generalisation. Approaches: expert review · multiple annotation — several annotators label the same data and disagreement marks a defect, measured as inter-annotator agreement (Cohen’s Kappa, or plain percentage agreement) · risk-based prioritisation of what to re-check, targeting ambiguous or near-boundary samples and whatever matters most for success or safety · comparison against similar datasets · rule checks (bounding boxes must not overlap or run off the image) · model-based — samples with high loss are likely mislabelled, ambiguous, or outside the training distribution.

In practiceExpert review sets the labelling guidelines early, IAA refines them, model-based checks keep finding stragglers as the model develops.

And the risks behind all five

Data from untrustworthy sources or poorly managed → provenance testing. Out-of-range values and wrong data types → constraint testing. Sub-optimal feature selection → feature testing. Augmentation that skews the set, missing data, uncovered value ranges, ambiguous data, poor annotation → the checks above.

Keep in mindPipeline performance can degrade in operation, and an uncontrolled change to the pipeline is a security event.

5Model testing — seven techniques, and when each earns its keep

This is where the AI-specific test design lives. Several of them exist purely to work around the missing oracle.

ML functional performance statistical

Accuracy, precision, recall and F1 measured against acceptance criteria — but stated with a margin of error and a confidence level, which together fix the minimum number of tests you need. It moves the result from one verdict to a measurement.

98 % accuracy · ±1 % MoE · 95 % CL → 601 tests, of which ≥ 589 must pass CT-AI §6.1.3, illustrative. Sequential testing allows early stopping: if accuracy holds, ~170 tests can already settle it.

Adversarial testing fragile inputs

Feed the model perturbations a human would not even notice, designed to make it predict wrongly. Inputs that succeed are adversarial examples, and they show where safeguards are needed — against accidental ones as much as against deliberate attacks.

Black box: build an equivalent model whose internals you know, craft examples there, and rely on transferability — or brute-force a vast number of variants and hope some land. White box: knowing the architecture, parameters and training process makes crafting them much easier.

Tiny exampleA few pixels changed on a stop sign and the classifier reads a speed limit.

Metamorphic testing no oracle needed

Take a source test case that passed, change its input by a known rule — a metamorphic relation — and check that the output changed the way the relation says it must. You never need to know the correct answer, only the relationship between answers.

Three common objectives: consistency (outputs align across related inputs), monotonicity (output moves directionally with the input), invariance (output stays stable under a perturbation). Derive the relations from domain knowledge, requirements or domain properties such as physical law; validate them by expert review and by running them against reference models.

Tiny exampleA risk model predicting age at death: raise the cigarettes-per-day input and the prediction must go down. You never needed the true age.
LimitWrong or incomplete relations give false confidence. MT finds relational flaws, not all absolute errors — pair it with other techniques.

Drift testing after release

Data drift — the incoming data no longer looks like the training data (user behaviour shifted, seasonality, a new kind of phishing). Concept drift — the meaning changed: the right answer for the same input is now different, so the learned decision boundaries are outdated.

Dynamic drift testing needs current ground truth from user feedback — direct (a rating) or indirect (what they actually watched) — and compares it against the model output with a threshold. Static drift testing needs no ground truth: it compares the statistical distributions of input and predicted output over time, e.g. with a Kolmogorov-Smirnov test.

Tiny exampleNew regulation turns a “low-risk” transaction type into a high-risk one. Nothing in the code changed; the model is now wrong.

Over- and underfitting during training

Overfitting: the model learned the noise instead of the pattern, so it generalises badly. Detected when it scores significantly worse on a separate test set — one that deliberately includes less common examples — than on validation. Underfitting: too simple, or the training data lacks features carrying the relationship. Detected when metrics stay low on both training and validation, and the learning curves stay high and close together without improving.

Tiny example99 % on training data, 71 % on anything new — classic overfit.

A/B testing pick a winner

Same inputs, two variants, results compared statistically to decide which is better — often in production, with traffic split between them. It uses the existing system as a partial oracle. It does not design test cases for you and gives no guidance on how to.

Use it to confirm an update performs at least as well as the version it replaces, and for self-learning systems: after a change, compare, keep it if improved, revert if not. Usual statistics: t-test, z-test, chi-squared, Mann-Whitney U.

Tiny exampleRouting algorithm v2 vs v1 compared on average commute time over consecutive weeks.

Back-to-back testing pseudo-oracle

Run the same inputs through an independent second implementation and compare the outputs. You only generate inputs, never expected results — so you can run enormous numbers of them, including inputs generated automatically from training data.

The pseudo-oracle must not share components with the system under test, or a shared defect makes both wrong in the same way — a real risk given how much open-source AI code is reused. Ideally a different team, different framework, different algorithm; conventional software counts if it solves the same problem. It only has to match functionally, which keeps it affordable.

Best momentMigrating to a new environment — development to production — and comparing results across edge cases.
A/B vs back-to-backA/B compares two variants on performance metrics to pick a winner. Back-to-back compares against a reference to find defects.
◆Before any of this: review the model documentation — intended use, training data provenance, known limits, version. A review finds the mismatch between what the model is for and what it is about to be used for, which no amount of test execution will.

6GenAI & LLM systems — testing something that writes back

Generative systems produce text, images, video and audio. Correctness becomes coherence, originality, plausibility and adherence to domain rules — and the input space explodes.

The input explosion problem why it is hard

There is an optional system prompt and a user prompt, each able to carry enormous and disparate data; there is an API path as well as a UI; there are parameters — temperature, maximum tokens — that change the output; and the context window keeps earlier turns alive and influencing everything after.

ConsequenceYou cannot enumerate the input space. Sample it deliberately and record the parameters with every result, or the result is not reproducible.

Benchmarks standardised

Curated datasets and tasks that let you compare models consistently — language understanding, reasoning, coding. Systematic and reproducible, which ad-hoc prompting is not.

Use it for“Is the new model version better than the one we run today?” — not for “is our feature correct?”.

A second model as judge automation

Manual review is often unavoidable, and pass/fail then rests on qualitative criteria that must be written into the requirements. Where it can be automated, a second GenAI system determines the result — for instance an image recognition system checking a generated image.

CarefulThe judge can reproduce the same biases and the same errors as the system it judges.

Red teaming fault attack

Deliberately pushing the system to produce harmful or undesirable output — privacy violations, hateful content, dangerous instructions. What it finds is then used to strengthen the system. Usually black box, usually end-to-end, and increasingly a regulatory expectation (EU AI Act).

The core activity is interactive multi-turn prompting, typically 15–20 turns. The loop: 1) assemble a diverse team to cover many perspectives and attack vectors 2) give it access in a safe test environment 3) probe, open-ended or by checklist 4) analyse the failures to understand the threats 5) turn them into datasets that drive mitigations.

ScopeNot just security. Also reliability, privacy, fairness, bias and misinformation — and for safety the point is often harmful output under ordinary use, with no attacker at all.
Coverage at scaleCrowd-sourced prompt generation, or one LLM generating attack prompts while another checks the outputs. Hybrid works best: human creativity, machine scale.

Red vs blue before vs during

Red teaming is proactive and pre-deployment — best run after internal quality checks, before release. Blue teaming is the running defence: ongoing real-time monitoring and filtering of live input. What red teaming finds is what blue teaming should then watch for.

Security specificsIndirect prompt injection, and malicious content hidden in documents the RAG retrieves.

Non-functional, same as ever

Resource utilisation during inference and training, because it is a direct cost: CPU and GPU usage, memory consumption, network bandwidth, response times.

Tiny exampleAnswer quality is fine; the per-request cost makes the feature unshippable.

7Deployment and the watch afterwards

An ML system is released into an environment that keeps moving. These checks exist because “it worked in training” is not a release criterion.

Install & uninstall

Install, upgrade and uninstall cleanly across every supported environment — including system dependencies such as GPU drivers, framework compatibility, and the installation scripts themselves.

Tiny exampleWorks on the dev box, fails on the edge device with the older driver.

Rollback test it first

Restore the previous working state after a degraded or failed deployment — model only, or the whole system including the data pipeline. It has to be exercised before deployment; a rollback first attempted during an incident is not a rollback.

Tiny exampleNew model ships, accuracy drops, previous version is back in minutes.

Canary release a slice of real users

Release to a small share of production traffic — say 5 % of users — and watch real-time metrics such as latency, accuracy and error rate to detect regressions before the full rollout.

Tiny example5 % of users on v2 for a day; error rate doubles; the rollout stops there.

Shadow testing zero user risk

Route the same requests to both the new and the current system, without affecting the live responses. It compares old and new on live data in a controlled, low-risk setting, and uncovers performance regressions and data drift before full deployment.

Tiny exampleTwo weeks of shadow traffic show the new model is better overall but worse on one customer segment.

Format conversion & portability

A model converted from its training format into a deployment format must keep consistent behaviour and acceptable operational efficiency — inference speed, memory use. Then confirm it across every target, from mobile and edge devices to cloud servers.

Tiny exampleQuantising for mobile costs 4 points of accuracy — a release decision, once you know.

Monitoring is the test that never ends

Drift testing (§5) belongs here: static distribution comparison always, dynamic comparison against user feedback where ground truth exists. Plus API testing of inputs, outputs, error messages and the integrations around the model — data feeds, clients, the pipeline.

Keep in mindFor an adaptive system, monitoring is the regression suite — the behaviour you signed off is not the behaviour it will have next month.
◆Development-side risks worth a review rather than a test: sub-optimal algorithm or framework choice · wrong hyperparameters · defective allocation of data to the training, validation and test sets · a weak evaluation approach such as skipping k-fold cross-validation · non-reproducible results from the stochastic nature of learning · framework security vulnerabilities and poor framework documentation.

8The other direction — testing with GenAI

CT-GenAI covers the opposite case: the product is ordinary, and the LLM is your tool. The tool is confidently wrong sometimes, so its output is itself a test object.

Three failure modes know the difference

Hallucination — factually wrong or irrelevant output: fictitious test cases, scripts that do not run, tests verifying acceptance criteria that do not exist. Reasoning error — misread conditional logic, cause and effect, or step-by-step problem solving; LLMs pattern-match rather than reason, so test planning, estimation and prioritisation are where this bites. Bias — inherited from training data; shows up in generated test data and in how acceptance criteria get rewritten.

Tiny exampleThe model generates a beautiful test suite for a field the spec never mentions.

Detecting them

Hallucination: cross-reference against the test basis and known system behaviour (automatable against established sources), expert review, and consistency checks across several answers. Reasoning: review the chain of reasoning for coherence, and execute the generated testware against the real test object — which settles it. Bias: check what the output over- and under-represents relative to the test strategy.

How much of thisScale it to the estimated risk of the task. Generated smoke tests ≠ generated safety-critical tests.

Mitigating them

Give full context in the prompt · split the work into steps with prompt chaining and verify each output before moving to the next · use structured, straightforward input formats · ground the model in your own documents with RAG · and cross-check by running the same task on several models and comparing the outputs.

Non-determinismLower the temperature, which narrows the probability distribution at the cost of variety, and fix the random seed. Neither gives full reproducibility — so automate the verification instead of relying on identical reruns.

Evaluate, then refine the loop

Judge GenAI output on accuracy against expert-written tests or the requirements, precision, recall (do the generated cases cover the valid and invalid partitions?), relevance and contextual fit to the test basis, diversity of behaviours and edge cases, execution success rate (do the scripts even run?) and time efficiency versus doing it by hand.

Then refine: iterate on wording and context · A/B two prompt versions against those metrics · analyse the error types you keep getting · ask the testers who use the output · and try both longer and shorter prompts, since more context does not always win. Share what works as a prompt library.

Because output variesThe metrics have to be computed over a statistically relevant sample, not over one impressive answer.

RAG and agents the infrastructure

RAG chunks your documents (roughly 256–512 tokens), embeds them in a vector database, retrieves the semantically closest chunks at query time and hands them to the model as context — which is how the answers get grounded in the current specification instead of in training data. LLM-powered agents go further: they call predefined functions — “tools” — and act on external systems, semi- or fully autonomously, sometimes several agents orchestrated together.

Keep in mindAgents inherit every failure mode above, and now they act on it. Automated verification of their results, or semi-autonomous mode for anything critical.

Privacy, and shadow AI policy, not technique

Test data and specifications pasted into a public model may be stored, reused for training, or exposed — a GDPR problem as much as a security one. Shadow AI — staff using unapproved tools on their own — turns that into unmanaged data leakage, compliance exposure and intellectual property disputes.

The fix is organisationalAn agreed strategy, approved tools, and clear rules about what may be pasted where.

The testing process — one cycle, seven activities

This page is pure theory: not which system to test, but how the work of testing is structured — whatever the system. Every project does some version of these seven activities. They are not a waterfall: analysis, design, implementation and execution overlap and repeat every iteration, and monitoring & control runs alongside all of them, start to finish. The map below walks the cycle in order; the sections after it go one activity at a time, then close with work products, traceability, the two testing roles, and the test-strategy choices that shape planning.

1Test planning

Defines the objectives of testing, then picks the approach that reaches them most effectively within the constraints of the context. It is revisited whenever the plan drifts from reality, not written once and filed away.

What a test plan documents ISO/IEC/IEEE 29119-3

Scope, objectives and test basis; assumptions and constraints; stakeholders and their roles, needs and training; how and how often information gets communicated; the risk register; the approach — levels, types, techniques, work products, entry/exit criteria, independence, metrics, data and environment needs; and the budget and schedule.

Entry & exit criteria gatekeeping

Entry: resources, testware and a baseline level of quality (e.g. a smoke test passes) are in place before a level starts. Exit: coverage reached, defects below an agreed density, or a binary yes/no such as "all planned tests ran". Running out of time or budget is a valid exit criterion too, if stakeholders knowingly accept the residual risk. In agile these are usually called Definition of Ready (entry, per story) and Definition of Done (exit).

Four estimation techniques

Ratio-based (reuse a dev:test ratio from past projects), extrapolation (measure the first iterations, project the rest), Wideband Delphi / planning poker (experts estimate alone, compare, repeat until they converge), and three-point: E = (a + 4m + b)/6 with error SD = (b − a)/6, from an optimistic (a), most-likely (m) and pessimistic (b) guess.

Prioritizing test cases

By risk (cover the biggest risks first), by coverage (maximise coverage, or prioritise whatever adds the most new coverage), by requirement or business priority, or by history (run whatever has failed most often, first).

Planning in iterative lifecycles

Release planning shapes the product backlog and the approach for every iteration ahead: testable user stories, acceptance criteria, project/product risk input, a release-level effort estimate. Iteration planning works one backlog at a time: detailed risk analysis per story, testability, splitting stories into tasks and estimating each one.

◆A test plan does not invent its approach from scratch — a mature organization leans on an existing test policy and test strategy. See section 9.

2Test monitoring and control

Two linked activities that run continuously from planning through completion — not a stage you pass through once.

Monitoring vs. control

Monitoring is the ongoing comparison of actual testing against the plan. Control is acting on that information — issuing directives that keep testing on track for its objectives.

What gets measured

Project progress (tasks done, effort spent); test progress (cases implemented, run, passed/failed; environment readiness); product quality (availability, response time, time between failures); defects (count and priority found/fixed, defect density, detection rate); residual risk; coverage (requirements, code); and the cost of testing itself.

Test progress report recurring

Issued regularly — daily, weekly — covering the period, progress against schedule and any deviations, impediments and how they were worked around, the metrics above, new or changed risks, and what is planned for the next period.

Test summary report at completion

Written once, at a milestone: a summary of testing, a quality assessment against the original objectives and exit criteria, deviations from the plan, impediments met, the metrics gathered, unmitigated risks and open defects, and lessons learned.

Typical control actions

Re-prioritising tests when a risk materialises; re-checking entry/exit criteria after a fix lands; rescheduling because the environment slipped; pulling in more resources when needed.

3Test analysis — "what to test"

Turns the test basis into a prioritized list of testable conditions, before a single test case gets written.

From test basis to test conditions

Analyse the test basis to find testable features, then define and prioritize the test conditions tied to each one — weighted by the risk and the level of risk they relate to.

Defects found before a test exists

Reading the test basis closely often surfaces ambiguous, missing or contradictory requirements on its own. These get reported like any other defect — analysis is already a defect-finding activity, not only a preparation step.

Testability

Is the item specified clearly and completely enough to test? Is it accessible and controllable — hooks, logs, observable outputs — or does it only expose a black box with nothing to check against?

Where test techniques come in

Black-box, white-box and experience-based techniques (see the Manual testing tab) are the toolbox analysis reaches for, so conditions come from a systematic method rather than from guesswork.

Measurable, not vague

Conditions are written so they can later be counted. "Every documented error message is produced at least once" is testable; "the error handling is good" is not.

4Test design — "how to test"

Converts each test condition into one or more concrete test cases, plus everything the cases will need in order to run.

Conditions become cases

Each condition becomes one or more test cases — or test charters, for an exploratory session — guided by coverage items that pin down exactly which inputs to pick.

Anatomy of a test case

An identifier, preconditions, the input or action, the expected result, and any post-conditions. A good case traces back to the condition(s) it was built to cover.

Test data requirements

Which values, records and combinations the cases need get decided here — and get built later, during implementation.

Test environment design

Hardware, network, stubs, drivers, simulators, virtualized services and any other tool or infrastructure piece the cases will depend on.

◆Design is still spec-based thinking — it does not decide who will run the case. Manual vs. automated is a choice made afterward, in implementation.

5Test implementation

Builds or acquires everything the test cases need to actually run. This is where "testware" stops being a description and becomes something executable.

Procedures & suites

Test cases are ordered into test procedures (scripts), then grouped into test suites for efficient, coherent execution.

Scheduling execution

Procedures are prioritized and arranged into a test execution schedule, so the cases that matter most run first regardless of what happens to the rest of the run.

Scripting

Manual scripts are written up for a person to follow step by step; automated scripts are coded against the chosen framework (see the Automated testing tab).

Building the environment

The test environment is assembled and verified to be correctly configured before the first test runs against it — not discovered to be wrong afterward.

Traceability check

Implementation is also where the bi-directional link — test basis → conditions → cases → scripts — gets verified, not assumed to still hold.

6Test execution

Running the tests per the schedule, manually or with a tool, and reacting to whatever comes back.

Forms it takes

A scheduled test run, continuous testing inside a pipeline, or a paired/exploratory session — same activity underneath, different cadence.

Comparing & logging

Actual results are compared against expected results; every run is logged — what ran, against which build or version, pass or fail.

From anomaly to defect report

A failure is analysed for its likely cause before it gets reported, so the report already points roughly at where the problem lives rather than just describing the symptom.

Confirmation & regression

A confirmation test (retest) checks that a specific fix worked; regression testing re-runs unrelated tests to check that nothing else broke along the way.

7Test completion

Closes out a chunk of testing at a milestone and turns it into knowledge the next cycle can reuse, instead of letting it evaporate.

When it happens

A test level finishes, an agile iteration ends, the project ends or is cancelled, or a maintenance release ships.

What gets checked

Every open defect report, change request and backlog item left over from the testing just finished is accounted for — closed, deferred or consciously carried forward, never silently dropped.

What gets kept

Testware worth reusing is identified and archived, or handed over to whoever maintains it next; the test environment is shut down in an agreed, reproducible state.

What gets written

A test summary report for stakeholders (section 2), plus a short retrospective — what worked, what should change next time.

8Work products, traceability and the two roles

Every activity above leaves something behind, and all of it should trace back to the test basis it came from.

Work products, by activity

Planning: test plan, schedule, risk register, entry/exit criteria. Monitoring & control: progress reports, control directives, risk updates. Analysis: prioritized test conditions, defects against the test basis. Design: prioritized test cases, test charters, coverage items, data and environment requirements. Implementation: test procedures, scripts, suites, data, environment components. Execution: test logs, defect reports. Completion: test summary report, lessons learned, change requests.

Why traceability matters

Linking test basis → conditions/cases → results → defects lets you prove coverage, scope the impact of a change, support an audit, and turn "70% of code is covered" into something a stakeholder can actually act on.

Two roles, not two people

A test management role owns planning, monitoring, control and completion. A testing role owns analysis, design, implementation and execution. One person often holds both; in agile the team usually absorbs the first role, and only cross-team concerns go to a test manager outside it.

9Test strategy — the choice behind planning

Advanced-level material. A test strategy is the organization's general, reusable approach to testing; a test plan is what one project does with it. Real strategies are usually a blend of several of these, not a single pure choice.

Analytical e.g. risk-based

Conditions are derived from analysing the test basis — risks, requirements — rather than decided up front.

Model-based

Build a model of the real or expected environment, inputs and behaviour — e.g. an operational profile for performance testing — and test against that model.

Methodical

A pre-agreed checklist or quality standard (e.g. ISO/IEC 25010 characteristics) applied the same way every release.

Process- or standard-compliant

Follow a process mandated from outside the test team — a regulator, or a framework's own ceremonies, such as Scrum's per-iteration acceptance criteria — rather than one the team designed itself.

Reactive

Design and run tests only once the software exists, reacting to its actual behaviour. The natural home of exploratory and attack-based testing.

Consultative

Test conditions come mainly from a key stakeholder's input — e.g. a prioritized browser/OS matrix handed to an outsourced test vendor.

Regression-averse

Heavy automation aimed specifically at the risk of regression, re-run on every change.

◆A test strategy also states the levels it governs and their entry/exit criteria, and can cover integration order, independence, environments, automation, tool choice, reuse, retest vs. regression, reporting, metrics, defect management, configuration management and roles — all consistent with the organization's test policy.

Automated testing — how a suite should be built

Writing a script that clicks or calls something is the easy part. What decides whether a suite is still trusted a year later is its structure: which tests are automated at which level, how the code is layered, what one test looks like inside, who owns the state it leaves behind, and how it waits for a system that answers asynchronously. A suite that fails at random, or passes while the product is broken, is worse than no suite. Every box below is clickable.

1Why automate, and what automation is not

Automation does not find new defects by itself. It re-checks, cheaply and quickly, things somebody already decided are worth checking.

What it buys you the point

Fast, repeatable regression on every change; checks a human cannot do well (thousands of combinations, exact numbers, timing); and a living specification — a readable test says what the system is supposed to do.

Tiny exampleAfter every hedger deploy, the same exposure scenarios run in minutes and give the same verdict for the same build.

What it does not replace limits

Exploratory testing, usability, judging whether a requirement makes sense, and anything whose expected result nobody can write down. An automated test only checks what it was told to check — it is blind to everything next to it.

Keep in mindA green suite means “the checks we wrote still pass”, not “the product works”.

Automation is software treat it so

A test suite has its own code, architecture, reviews, defects and technical debt. It deserves the same standards as production code: version control, review, naming, no copy-paste, refactoring.

Rule of thumbIf nobody would accept the code in the product, it should not be accepted in the tests either.

Trust is the product the real metric

A test is useful only if a red result reliably means “something is broken” and a green one reliably means “this behaviour still works”. False alarms teach people to ignore failures; false passes hide them.

Tiny exampleOne test that fails every third run for no reason makes the whole team rerun the pipeline instead of reading the failure.

2Strategy — what to automate, and at which level

The cheapest test that can catch a defect is the right place for it. Push checks down to the lowest level that still sees the behaviour.

The test pyramid shape of a suite

Many fast unit tests at the bottom, fewer service / API tests in the middle, a thin layer of end-to-end tests on top. Lower tests are faster, more precise about where the defect is, and less brittle; higher tests prove the parts work together.

Anti-patternThe “ice-cream cone”: mostly UI end-to-end tests and almost no unit tests — slow, flaky and vague about the cause of a failure.

What each level is for the layers

Unit — one function or class, no network, milliseconds. Integration / contract — two components and the agreement between them (request and response shape). API / service — a deployed service through its real interface. End-to-end — a user flow across several services.

In our suiteThe hedger tests are service-level: real PLAT and CORE gateways on test-env, no UI. That is the right level for exposure and routing rules.

Choosing what to automate selection

Automate what is run often, is stable, is risky if it breaks, has a clear expected result and is tedious or error-prone by hand. Leave out one-off checks, features still changing every week, and anything whose oracle is a human opinion.

Rule of thumbEvery regression bug that reached production is a candidate for a test at the lowest level that would have caught it.

Return on investment cost is ongoing

The cost of a test is not writing it — it is running, debugging and updating it for as long as it exists. A test pays off when (runs × manual cost saved) exceeds (build + maintenance + time lost to false failures).

Tiny exampleA brittle UI test rewritten after every redesign can cost more than doing the check by hand.

3Architecture — layers, so a change touches one place

The test says what is checked; lower layers know how to talk to the system. When an endpoint changes, one helper changes — not forty tests.

The generic architecture (gTAA) ISTQB TAE

Four layers: test generation (where cases come from — written by hand, from models or data), test definition (the test cases and their data), test execution (runner, setup, logging, reporting) and test adaptation (the code that actually talks to the system under test).

Why it mattersEach layer can change without rewriting the others: a new runner, a new API version, new data.

Adaptation layer clients & helpers

API clients, page objects or protocol helpers that hide URLs, auth, payload shapes and parsing. Helpers are named after the business action (open_market_order, enable_all_assignments), not after the HTTP call.

In our suiteutils/http.py (transport, tokens) → utils/methods/*_utils.py (business actions) → tests/… (scenarios only).

Configuration out of code one place

Environment URLs, accounts, symbols and timeouts live in configuration, not scattered through tests. Secrets never sit in the repository. The same suite must run against another environment by changing configuration only.

In our suiteutils/config.py plus the mcp-server vault for tokens; tests never contain a password.

Scripting approaches how tests are written

Linear (recorded, copy-pasted steps) → structured (shared functions) → data-driven (one script, many data rows) → keyword-driven (tests composed from business keywords) → model-based (cases generated from a model). Higher approaches cost more to start and much less to maintain.

Tiny example@pytest.mark.parametrize over volumes and sides is data-driven: one test body, every row reported separately.

4Anatomy of one good test

Someone who has never seen the test should understand from its name and body what is checked, and from its failure message what went wrong.

Arrange – Act – Assert three blocks

Arrange the preconditions, act once — the behaviour under test — and assert on the outcome. Given-When-Then is the same idea in business language. Mixing the blocks (assert, act again, assert) usually means two tests in one.

Tiny exampleArrange: rule on, account 1004 disabled. Act: client 1001 buys 30 lots SYMBOL1. Assert: 1004 received no order, the others got the split.

One behaviour per test focus

A test checks one rule, so a failure points at one cause. The name states the rule and the expected outcome — test_disabled_hedger_gets_no_share, not test_hedger_3. Several assertions are fine when they describe the same outcome.

SmellA test called “full flow” that fails on step 7 of 12 tells you nothing until somebody reads the log.

Assertions that explain the failure is the report

Assert on exact expected values derived from the specification, not on “something came back”. Put the context in the message: expected, actual, the account and the step. Never assert on a value the test itself calculated the same way as the product.

Tiny exampleassert vol == 6, f"1002 should hedge 6 lots, got {vol}" beats a bare assert vol.

FIRST properties to check

Fast enough to run often, Independent of other tests and their order, Repeatable in any environment and on any run, Self-validating (pass or fail, no reading logs to decide) and Timely — written with the change, not months later.

CheckRun the suite in random order and twice in a row. Anything that changes the verdict breaks I or R.

5State and data — the test owns what it touches

Most unstable suites are not unstable because of timing but because tests share state: an account, a rule, an open position left by the previous test.

Fixtures setup in one place

The known state a test starts from, built by shared, named fixtures instead of copy-pasted setup. Scope is chosen deliberately: per test for anything the test changes, per module or session only for expensive, read-only things (a login token, a downloaded instrument list).

In our suiteautotest_rule in tests/hedger/conftest.py prepares the AUTOTEST hedge rule for each test.

Teardown that always runs leave it clean

Restore what was changed in a yield fixture or finally, so it runs even when the assertion fails. Then verify the clean state rather than assuming it — the next test depends on it.

In our suiteExposure is zeroed only after the rule is on and every matrix account is isEnabled=true, then the state is read back to confirm it is 0.

Test data known, owned, unique

Data a test creates should be unique (ids, ClOrdIDs, names with a run suffix) so parallel or repeated runs do not collide. Shared environment data is read, not assumed — and shared resources are reserved for automation or locked while a suite runs.

Rule of thumbNever let a test depend on data another test created. Builders or factory helpers make the needed data explicit.

Test doubles Meszaros

Dummy (filler, never used), stub (canned answers), spy (records calls), mock (expects specific calls), fake (a working lightweight implementation, e.g. an in-memory FIX acceptor). They make lower-level tests fast and deterministic; service-level tests use the real thing.

In this appThe FIX client tests run against a fake acceptor on localhost — logon, orders and logout are checked without test-env.

6Reliability — waiting, retries and flaky tests

A flaky test passes and fails on the same code. It is a defect — in the test, the environment or the product — never background noise.

Wait for a condition, not for time no sleep

Asynchronous systems need waiting, but a fixed sleep(5) is either too short (flaky) or too long (slow). Poll for the expected state with a timeout and a clear message when it never arrives.

Tiny example“Poll positions every 0.5 s for up to 10 s until 1002 shows 6 lots” instead of “sleep 10 s, then read once”.

Retries are not fixes be honest

Retrying a check that races with eventual consistency is legitimate. Re-running a whole failed test until it passes hides the defect. If a test needs a rerun to pass, that is a finding, not a pass.

In our suiteutils/retry.py retries a verify step on AssertionError only — and its docstring says a test that needs it to pass at all belongs in the bug registry.

Quarantine, then fix contain it

A known-flaky test is moved out of the gating run with a ticket and an owner, so it does not train people to ignore red builds — and it comes back once fixed. Typical causes: shared state, order dependence, timing, test data collisions, unstable environment.

Rule of thumbQuarantine with a deadline. A quarantine nobody looks at is deleted coverage.

The environment is part of the test shared ground

Service-level suites run on a shared environment. Two suites changing the same rule at once will both fail for reasons neither caused. Serialise runs that share resources, and check the environment is healthy before blaming the product.

In our suiteOnly one pytest run at a time on test-env, and an unreachable environment is reported as “unverified”, not as test failures.

7Running it — pipeline, tags, reports

A suite nobody runs automatically decays. Wire it into the delivery pipeline, and make its output usable by someone who did not write it.

In the pipeline continuous

Fast checks on every commit, the service-level suite on every deploy to the test environment, long or costly suites nightly. A failure blocks the change it belongs to — feedback within minutes, not a week later.

Rule of thumbThe longer the gap between the change and the failure, the more expensive it is to find the cause.

Tags and selection run what you need

Markers group tests by area, risk or cost so a run can be selected: smoke only, everything touching trading, one service. Strict markers stop a typo from silently creating a new, empty group.

In our suitepytest.ini defines PLAT, CORE, ADMIN, MANAGER, TRADING and SMOKE with --strict-markers.

Reports with evidence traceable

A useful report says which behaviour failed, on which build and environment, with the requests, responses and values that prove it — and links the test to the requirement or ticket it covers.

In our suiteutils/scenario.py attaches the scenario to the report, so a failure reads as a test case, not only as a stack trace.

Maintenance continuous, not a project

Review tests like code; delete tests that no longer check anything meaningful; refactor helpers when the same steps appear in several tests; track the suite's run time and flaky rate as health metrics.

SmellA test nobody understands but nobody dares delete. Either document why it exists or remove it.

8Test smells — signs the structure is wrong

Each smell has a structural cause. Fixing the cause fixes every test that shows it.

SmellWhat you seeStructural fix
Fragile testBreaks on changes unrelated to what it checksMove endpoint and payload details into the adaptation layer
Erratic (flaky) testSame code, different verdictsIsolate state, poll instead of sleep, unique test data
Interacting testsPasses alone, fails in the suite (or the reverse)Per-test fixtures with guaranteed teardown and a verified clean state
Obscure testYou cannot tell what is checked without reading helpersBusiness-named helpers, Arrange-Act-Assert, a name that states the rule
Assertion rouletteMany bare asserts, a failure says only “AssertionError”Assertion messages with expected, actual and context
Conditional test logicif / try deciding what to assertSplit into tests with fixed preconditions; a test has one path
Test code duplicationThe same ten setup lines in every fileFixtures and helpers; data-driven parametrisation
Slow suiteNobody runs it before pushingPush checks down the pyramid; wait for conditions; run in parallel where state allows
Green but blindPasses while the feature is brokenAssert on exact expected values from the spec; see a test fail before trusting it

9How to choose — the short version

Same logic as the other pages: start from the problem you have, and the structural answer follows.

SituationReach forWhy
A business rule with clear inputs and outputsUnit or service-level test, data-drivenCheapest level that still sees the rule; one body, many rows.
Two services must agree on a messageContract testCatches a broken agreement without a full end-to-end environment.
A user flow across several systemsA few end-to-end testsProves the integration; keep them few, the detail lives lower down.
The system answers asynchronouslyPolling with a timeoutWaits exactly as long as needed and fails with a reason.
Tests fail only when run togetherPer-test fixtures, verified teardownThe cause is shared state, not the assertion.
An endpoint change broke forty testsAdaptation layer / helpersThe next change touches one function.
A dependency is slow, costly or unavailableTest double (stub or fake)Deterministic and fast; keep a few tests against the real one.
A test fails at randomQuarantine with an owner, then root causeProtects trust in a red build while it is fixed.
A production bug escapedRegression test at the lowest level that catches itTurns the incident into a permanent check.
◆Three things worth memorising. First: a suite is only as valuable as it is trusted — one flaky test costs more than it catches. Second: structure beats volume; layers and fixtures decide the maintenance cost of every future test. Third: never trust a test you have not seen fail.
◆Test design comes first. Automation executes test cases; it does not choose them. Equivalence partitioning, boundary values and decision tables from the Manual testing tab decide which cases are worth automating.
