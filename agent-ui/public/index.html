Manual testing on one page

Start at the top of the tree and walk down: how much of the internals you can see, what size of thing you are testing, whether you check what it does or how well it does it, and finally which technique tells you which test cases to write. Every box below links to its explanation.

1How much you can see inside

The first fork in the tree. It decides when you can write the test and what it survives.

Black box spec-based

Test from the outside, using only the specification. You never look at the code, so the test still works after the code is rewritten, as long as the required behaviour has not changed.

ExampleDeposit 0 USD and expect the message that the amount must be greater than 0.

White box structure-based

Test from the inside, using the code. You can only write these after the thing has been designed or written, and they break when the code is restructured.

ExamplePick inputs so both sides of if (balance > 0) run at least once.

Grey box mixed

You drive it from the outside, but you know some internals such as the database schema, the API contract or the log format, and you use that knowledge to check the result. Most QA work in this team looks like this.

ExampleSave a group in Admin, then check the row landed in the database.

Manual vs automation who runs it

Same techniques, different runner. A person exploring finds surprises a script never will; a script repeats 500 checks overnight without getting bored. Design the test first, then decide who runs it.

Rule of thumbNew and unclear → manual. Stable and repeated → automate.
◆Experience-based testing is a third family alongside black and white box: it leans on the tester’s knowledge instead of a document or the code. See section 7.

2Test levels and the size of the thing under test

Same product, four zoom levels. Each level finds a different kind of defect, so skipping one leaves a gap.

Unit and component smallest

One function or class, on its own, with everything around it faked. Fast, precise, and it points straight at the broken line. ISTQB calls this component testing.

ExampleThe swap formula returns 35 instead of 3.5 for 35 % at price precision 3.

Integration the seams

Two or more parts working together. Every part can be correct on its own while the pair is still wrong, for example because of mismatched units, swapped fields or a format nobody agreed on.

ExampleMCP → connector → PLAT: does the value survive all three hops unchanged?

System whole product

The complete system end to end, in an environment close to production, doing what a real user would do. This is where most manual testing happens.

ExampleOpen a position in the Manager and see it arrive in the LP session.

Acceptance the customer

Not in the diagram, but it is the level above system: does this actually solve the business problem? Run by or with the people who asked for it.

ExampleA user completes a full day of routine work on the new screen.

3Integration and the order of connecting parts

Only relevant at the integration level. It is a choice about how fast you go versus how easily you can tell what broke.

Incremental one at a time

Add one part, test, add the next. Slower to set up, but when something fails you already know it was the piece you just added.

ExampleAdd the router, test. Add the quoter, test. Add the config service, test.

Top-down needs stubs

Start at the top layer and replace everything underneath with stubs. You see the user-facing flow early, but the stubs take time to write.

ExampleTest the Admin screen against a fake API that always returns 3 groups.

Bottom-up needs drivers

Start at the lowest layer and fake the callers. The engine gets solid early, but nobody sees a working screen until late.

ExampleDrive the connector with a script instead of the real UI.

Non-incremental, also called big bang all at once

Connect everything first, then start testing. It is cheap to set up and tempting under a deadline, but a failure could be anywhere, so debugging is slow.

ExampleDeploy all services, click one flow, get an error with no idea which hop failed.

4Functional vs non-functional

Functional testing asks whether the system does the right thing. Non-functional testing asks whether it is good enough, and it has its own quality attributes.

Functional what it does

Behaviour against the rules: correct results, correct rejections and correct messages. The design techniques in sections 6 to 8 are used here.

ExampleA limit order fills when the price reaches the limit and not before.

Non-functional how well

Everything the feature must also be: fast, stable, usable, portable and secure. It is the same feature with a different question, and usually a different kind of defect.

ExampleThe same order fills in under 200 ms with 500 users online.

Usability can they use it

Can a real user reach their goal without being told how? Measured by observing people, not by reading the screen yourself.

ExampleA new user finds the setting in under a minute, unaided.

Compatibility elsewhere

Does it still behave correctly in other browsers, clients, versions or operating systems? The number of combinations grows quickly, which is why pairwise testing is used here.

ExampleSame MCP answer in Claude Desktop, Claude Code and Onyx.

5Four types of performance testing

They are not intensities of the same test. Each one answers a question the others cannot.

Load expected

Realistic, anticipated load from a controlled number of users, rising towards the target. Question: can it cope with the traffic we actually expect?

Shaperamp up → hold → ramp down
Example500 users, one query each per minute.

Stress past the limit

Peak load at and beyond the specified limit, or normal load with resources taken away. Question: how does it fail, and does it recover?

Shapepush past the maximum
ExampleGo to 2 000 users; then halve the container memory.

Scalability tomorrow

Ability to meet future requirements that exceed today’s. Question: how far can we grow before we breach the current targets? Once you know the ceiling, you can alarm on it in production.

ExampleStill under 1 s with 3× today’s accounts?

Stability and endurance over time

Steady load held for an operationally realistic period. Question: do resources such as memory, database connections or thread pools leak and degrade it hours later?

Example8 hours of steady load; memory flat at the end, not climbing.
◆Also in the family: spike, a sudden burst followed by a return to normal, concurrency, many users doing the same thing at the same moment, capacity, how many users or transactions the system can take before the targets are missed.
throughput = virtual users ÷ (processing time + think time) This is why 500 users is not a load. The same 500 users querying once a minute produce 30 000 queries per hour, while querying once an hour produces 500. That is a sixty times difference.

6Black-box techniques for selecting test cases

You cannot test everything. These techniques show which few tests carry the most information and give you a measure of how much has been covered.

Equivalence partitioning start here

Split each input into groups that the system should treat in the same way, then test one value from each group, including the invalid groups. Groups must not overlap and must not be empty.

ExampleVolume below 0, equal to 0, from 0.01 to 100 and above 100 gives 4 tests instead of 400.

Boundary value analysis the edges

Mistakes cluster at the edges of those groups. Test the boundary and its neighbour, which is 2-value analysis, or the boundary and both neighbours, which is the stricter 3-value analysis. It only works for ordered groups.

ExampleLedger limit 92 days → try 91, 92, 93.

Decision table combined rules

For business rules where several conditions combine. One column per rule; test every feasible column. It also exposes rules the spec forgot to state.

ExampleRetail client, sufficient margin and open market lead to fill, reject or queue.

State transition has states

Used for anything with a lifecycle. Test every valid transition, which is the usual target, and attempt the invalid ones, one invalid per test case, so one defect cannot hide another.

ExamplePending to Filled is valid, Pending to Cancelled is valid, Filled to Cancelled is invalid and should be attempted.

Pairwise too many combos

When full combinations are impossible, cover every pair of values instead. Small set, surprisingly strong: most failures come from one or two variables interacting.

Example4 clients × 3 languages × 3 roles = 36 → about 12 tests.

Classification tree draw it first

Draw the parameters and their values as a tree before choosing combinations. It does not produce test cases by itself but supports partitioning, boundary analysis and pairwise testing.

Exampleclient · browser · language · OS → then pick the pairs from the picture.

Use case testing real flows

One test for the main path, plus enough tests to cover every alternative path and every error path. This is closest to how the product is really used and is also useful for performance profiles.

ExamplePlace order → main path; no margin, market closed, LP down → 3 more.

Combine them usually best

They are not rivals. A decision table tells you which combinations matter; partitioning tells you which value to use inside each condition.

ExampleFor the decision table row where margin is not sufficient, choose a boundary value.
◆Empirical backing for pairwise: in a medical-device study, 66 % of failures came from a single variable, and single- plus two-variable interactions accounted for 97 %. The residual risk is failures needing three or more variables at once.

7Experience-based techniques for where other techniques end

No formal coverage number here. These find the defects a systematic technique walks straight past, and they work when documentation is thin or time is short.

Error guessing go for the throat

Attack the places defects usually hide, based on what has broken before in this team and this product.

Exampleempty list · 0 · null · a name with a trailing space · a date at midnight.

Exploratory timeboxed

A session with a charter, which is a goal, and a time limit. You design, run and learn at the same time, and each test follows from what the previous one showed.

ExampleSpend 60 minutes trying to break the ledger date filter and take notes as you go.

Checklist-based memory aid

A list of things worth remembering, not step-by-step scripts. Keeps coverage broad without freezing the tester into a fixed path.

ExampleCheck every list when empty, with one row, with 500 rows, sorted, filtered and exported.

8The two white-box coverage measures you will meet

Mostly a developer’s tool, but the numbers land in your reports, so it pays to read them correctly.

Statement coverage weaker

Every executable line runs at least once. If a line contains the defect, it has at least been executed, which gives it a chance to fail visibly.

ExampleAn if with no else: one test can already reach 100 %.

Branch coverage stronger

Every decision is taken both ways, true and false. Full branch coverage implies full statement coverage, but not the other way round.

ExampleSame if: now you need the skipped path too.

Reading any coverage number

Every technique in this page defines its own coverage items, such as partitions, boundaries, table columns, transitions, statements or branches. The percentage always means the same thing.

coverage % = items exercised ÷ items total × 100

9How to choose

There is no single best technique. The syllabus is blunt about it, and so is practice.

SituationReach forWhy
A field with rangesEquivalence partitioning + boundary valuesCheapest tests that still find the classic off-by-one.
Rules with several conditionsDecision tableExposes combinations and gaps in the specification.
Anything with a lifecycleState transitionInvalid transitions are where the silent bugs live.
Too many configurationsPairwise testing with a classification treeShrinks the set without losing most of the risk.
Whole user journeysUse case testingMatches how it is really used; reusable for load profiles.
Thin or missing specExploratory + error guessingWorks with no documentation at all.
A release you must not breakAll of the above, combinedSystematic gives breadth, experience gives depth.
◆Two things worth memorising. First, 100 % coverage does not mean that something is fully tested. It only means that the model has no more tests to give. Second, black-box and experience-based techniques are strongest together, because the second one covers the systematic blind spots of the first.
◆What drives the choice according to ISTQB: the type of project, the schedule, the information available and the skills of the testers.

Testing AI with the same craft and different rules

Everything on the manual-testing page still applies: an AI product is mostly ordinary software with one probabilistic part in the middle. What changes is that part. You often cannot say what the correct answer is, the same input may not give the same output twice, and the behaviour can change after release. The unit of testing therefore moves from a function to the data and the model, and a single passed test no longer means much on its own. Every box below links to its explanation.

Grounded in ISTQB CT-AI v2.0, Certified Tester AI Testing released on 2026-04-17, and ISTQB CT-GenAI v1.0, Testing with Generative AI released on 2025-07-25. Sections 1 to 7 cover testing a system that contains AI. Section 8 covers the opposite direction, using generative AI for testing.

1Why AI breaks normal testing

Four properties do all the damage. Everything else on this page is a response to one of them.

No test oracle the core problem

In normal testing you know the expected result, so pass or fail is obvious. With AI the expected result is often unknown, subjective or beyond what a person can check, and there is no agreed ground truth. Vague requirements make it worse.

ExampleIs this the best product recommendation? There is no right answer to compare against.

Non-determinism it varies

Probabilistic sampling, floating-point limits and GPU parallelism mean the same input can give a different output. One failed run proves nothing; one passed run proves even less.

ExampleThe model calls a cat a dog once in 200 runs, and a single test will never show that.

Locked vs adaptive does it change?

Locked, where behaviour is fixed after deployment, as in most deployed models. It is largely deterministic, so expected results stay valid. An updated model counts as a new system and is tested again. Adaptive, which keeps learning in production, for example through reinforcement learning, so its behaviour can change during the test. Most LLM products sit between: locked at runtime, updated periodically.

Rule of thumbAdaptive → you cannot pre-write tests for behaviour that does not exist yet. Build an automated core suite and re-run it on every change.

Statistics, not verdicts consequence

Because of these three properties, results are measured over a large and representative sample and reported as a rate with a confidence level rather than as a single verdict. The test suite has to be large enough to be statistically significant.

Example98 % accuracy, plus or minus 1 % at 95 % confidence, instead of a single passed test.
◆Ways round the oracle problem: define acceptable ranges and tolerances instead of exact values, fix the environment so that runs are repeatable, ask a domain expert, who can be wrong but provides a baseline, use metamorphic testing, which checks relations between outputs rather than the outputs themselves, use a pseudo-oracle, which is a second independent implementation described in section 5.

2Quality characteristics you can require

ISO and IEC 25059 extends the familiar 25010 model with characteristics that only apply to AI. Acceptance criteria are written against them.

AI functional correctness adjusted

Perfect accuracy is not achievable, so correctness is defined with an accepted error rate: both correct and incorrect outputs count, and a threshold says how many wrong answers are tolerable.

ExampleAt least 98 % of classifications are correct, instead of all classifications being correct.

AI robustness under pressure

Keeping that level of correctness with biased, adversarial or invalid input, external interference, adverse conditions or an operator misusing the system.

ExampleAccuracy must not collapse when the photo is blurred or the prompt is hostile.

Functional adaptability self-adjusting

Can the system adapt on its own to a changed operating environment after deployment, and does it do so correctly?

ExampleA drone switches flight mode when it crosses a set altitude.

User controllability & intervenability the off switch

A person or another agent can step in in time. Controllability is the general ability to intervene, while intervenability means intervening specifically to prevent harm.

ExampleManual override is offered the moment performance degrades by 30 %; full deactivation past 50 %.

Transparency can you explain it

The right information about the system reaches the people who need it: model version, data provenance, documentation, limits. Testable through reviews and through an API that reports it.

ExampleAn endpoint returns the deployed model’s version id and a link to its documentation.

Societal & ethical risk mitigation the broad one

Accountability, fairness and non-discrimination, privacy, safety and security, human control of technology, human-centred design, respect for the rule of law, environmental sustainability, labour practices.

ExampleEqual approval rates across protected groups, tested in section 4.
◆Acceptance criteria for AI are statistical, probabilistic or threshold-based, not binary. Write them that way before you start, or you will have no way to call a result passed.
◆Safety makes all of this harder: requirements start as vague goals encoded in training data, so traceability is poor. Non-determinism prevents guarantees. Self-learning moves away from what was tested. Decisions are hard to explain, and tools such as LIME help at a cost to performance. Functional safety standards have not caught up, while the EU AI Act already classifies AI used as a safety component as high risk.

3Test levels: two new ones in addition to the usual four

Component, integration, system and acceptance all still happen. An ML system adds two levels that have no equivalent in conventional software.

Input data testing new

The data is the specification, so it has its own level covering the training, validation and test datasets and the production data the model uses in operation. See section 4.

ExampleHalf of the training rows for one account type are missing. This is found here or never.

ML model testing new

The trained model is the thing under test, as the final output of the ML workflow before it is connected to anything else. See section 5.

ExampleMeasure accuracy, recall and robustness on a held-out set.

The conventional four, unchanged

Component, covering the non-AI parts such as data capture and communication. Component integration, confirming that the model receives the input and that its prediction reaches the rest of the system. API testing belongs here when AI is provided as a service. System, confirming that model performance holds after embedding, especially when the model was deliberately changed, for example a compressed DNN, together with non-functional checks such as prediction time. Acceptance, confirming that the service suits the intended system and that the ML performance criteria are met.

Watch outA model that is excellent standing alone can be mediocre once compressed and deployed. That is a system-level finding.

Risk-based, by workflow stage

Most regulatory frameworks require a risk-based approach. One usable split: development risks, such as a poor algorithm, a weak evaluation approach or framework vulnerabilities, covered in section 7, data risks, such as biased or unrepresentative data or a broken pipeline, covered in section 4, model risks, such as performance below target, overfitting or susceptibility to adversarial examples, covered in section 5.

AlternativeCategorise the risks by the ISO and IEC 25059 characteristics from section 2 instead.

4Input data testing, where the dataset is the specification

Most defects blamed on the model were already in the data. There are five kinds of check, and all of them can run before a single prediction is made.

Testing for bias fairness

Non-random and unfair differences in treatment based on sensitive attributes such as gender, age or race, which is often unlawful. There are two sources: data bias, meaning unrepresentative or poisoned training data, and algorithmic bias, meaning a threshold or rule that produces unfairness even with clean data.

Approaches: review how the data was collected and annotated and which populations it represents, use exploratory data analysis to find skewed distributions across sensitive attributes, and run a representative dataset through the system to look for statistically significant differences between groups. The last approach detects bias whether it comes from the data or from the model.

Disparate impact analysisSelect the sensitive attribute, build counterfactuals such as the same loan application with the gender changed, run them and analyse enough of them for a statistically significant result. This also works for combinations of attributes. Keep the counterfactuals realistic, otherwise you measure the reaction of the model to nonsense instead of its bias.

Data pipeline testing layered

Start with a design review. Component: ingestion, transformation scripts and sensor interfaces, checked with code review, static analysis, validation rules, error handling and a review of vulnerabilities that could let malware or poisoned data in. Component integration: data flows across internal interfaces and is interpreted correctly on the far side. System: smoke tests first, then functional tests of transformations and routing, then non-functional tests of load, scalability and security, and also fault injection with defective inputs. System integration: sources, storage, monitoring and the model downstream.

ExampleCompare the operational pipeline with the training pipeline. This finds the classic skew between training and serving.

Data representativeness does it match reality

How closely training, validation and test data match what the model will actually meet in operation. Catches skewed datasets, missing data, disproportionate feature distributions, operational scenarios with no coverage, and imbalanced classes.

Define the target population first using domain experts, data from existing or similar systems and benchmark datasets from trusted sources, then compare the characteristics of your dataset with it.

ExampleThe model will serve 40 % mobile users; the training set is 98 % desktop.

Dataset constraint testing schema for data

Write the rules the data must satisfy, like a database schema, then check them. Single-value constraints apply to one attribute in one instance, such as type, range or format. Multi-value constraints apply across instances, such as a total that must stay within bounds, a limit on duplicates or a limit on missing values, which is often zero.

ExamplePoints awarded across one race must be above 50.5 and not above 102. No single row can show this.

Label correctness testing supervised only

Wrong labels directly undermine performance and generalisation. Approaches: expert review · multiple annotation, where several annotators label the same data and disagreement indicates a defect, measured as inter-annotator agreement with Cohen’s Kappa or simple percentage agreement, risk-based prioritisation of what to re-check, targeting ambiguous or near-boundary samples and whatever matters most for success or safety · comparison against similar datasets · rule checks, for example bounding boxes must not overlap or extend beyond the image, model-based, where samples with high loss are likely to be mislabelled, ambiguous or outside the training distribution.

In practiceExpert review sets the labelling guidelines early, IAA refines them, model-based checks keep finding stragglers as the model develops.

And the risks behind all five

Data from untrustworthy sources or poorly managed → provenance testing. Out-of-range values and wrong data types → constraint testing. Sub-optimal feature selection → feature testing. Augmentation that skews the set, missing data, uncovered value ranges, ambiguous data, poor annotation → the checks above.

Keep in mindPipeline performance can degrade in operation, and an uncontrolled change to the pipeline is a security event.

5Model testing: seven techniques and when to use each

This is where the AI-specific test design lives. Several of them exist purely to work around the missing oracle.

ML functional performance statistical

Accuracy, precision, recall and F1 are measured against acceptance criteria and stated with a margin of error and a confidence level, which together set the minimum number of tests. The result becomes a measurement instead of a single verdict.

98 % accuracy · ±1 % MoE · 95 % CL → 601 tests, of which ≥ 589 must pass CT-AI §6.1.3, illustrative. Sequential testing allows early stopping: if accuracy holds, ~170 tests can already settle it.

Adversarial testing fragile inputs

Feed the model perturbations a human would not even notice, designed to make it predict wrongly. Inputs that succeed are adversarial examples, and they show where safeguards are needed against accidental cases as well as deliberate attacks.

Black box: build an equivalent model with known internals, create examples there and rely on transferability, or try a very large number of variants. White box: knowing the architecture, parameters and training process makes crafting them much easier.

ExampleA few pixels changed on a stop sign and the classifier reads a speed limit.

Metamorphic testing no oracle needed

Take a source test case that passed, change its input by a known rule, called a metamorphic relation, and check that the output changed in the way the relation requires. You never need to know the correct answer, only the relationship between answers.

Three common objectives: consistency, where outputs agree across related inputs, monotonicity, where the output moves in the same direction as the input, invariance, where the output stays stable under a small change. Derive the relations from domain knowledge, requirements or properties such as physical laws, and validate them through expert review and reference models.

ExampleA risk model predicting age at death: raise the cigarettes-per-day input and the prediction must go down. You never needed the true age.
LimitWrong or incomplete relations give false confidence. Metamorphic testing finds relational flaws but not all absolute errors, so combine it with other techniques.

Drift testing after release

Data drift, where incoming data no longer looks like the training data because of changed user behaviour, seasonality or a new kind of phishing. Concept drift, where the meaning has changed and the right answer for the same input is now different, so the learned decision boundaries are outdated.

Dynamic drift testing needs current ground truth from user feedback, either direct such as a rating or indirect such as what users actually watched, and compares it with the model output against a threshold. Static drift testing needs no ground truth: it compares the statistical distributions of input and predicted output over time, e.g. with a Kolmogorov-Smirnov test.

ExampleA new regulation turns a low-risk transaction type into a high-risk one. Nothing in the code has changed, but the model is now wrong.

Over- and underfitting during training

Overfitting: the model learned the noise instead of the pattern, so it generalises poorly. This is detected when it scores much worse on a separate test set that deliberately includes less common examples than on the validation set. Underfitting: too simple, or the training data lacks features carrying the relationship. Detected when metrics stay low on both training and validation, and the learning curves stay high and close together without improving.

Example99 % on training data and 71 % on new data is a classic case of overfitting.

A and B testing pick a winner

The same inputs are given to two variants and the results are compared statistically to decide which is better, often in production with traffic split between them. The existing system serves as a partial oracle. It does not design test cases for you and gives no guidance on how to.

Use it to confirm an update performs at least as well as the version it replaces, and for self-learning systems: after a change, compare, keep it if improved, revert if not. Usual statistics: t-test, z-test, chi-squared, Mann-Whitney U.

ExampleRouting algorithm v2 vs v1 compared on average commute time over consecutive weeks.

Back-to-back testing pseudo-oracle

Run the same inputs through an independent second implementation and compare the outputs. You only generate inputs, never expected results, so very large numbers of them can be run, including inputs generated automatically from training data.

The pseudo-oracle must not share components with the system under test, otherwise a shared defect makes both wrong in the same way. This is a real risk because so much open source AI code is reused. Ideally it comes from a different team, framework and algorithm. Conventional software also qualifies if it solves the same problem. It only has to match functionally, which keeps it affordable.

Best momentMoving to a new environment, for example from development to production, and comparing results for edge cases.
A and B testing compared with back-to-back testingA and B testing compares two variants on performance metrics to choose the better one. Back-to-back testing compares against a reference to find defects.
◆Before any of this: review the model documentation, including intended use, origin of the training data, known limits and version. A review finds the mismatch between what the model is meant for and what it is about to be used for, which test execution alone cannot find.

6Generative AI and LLM systems

Generative systems produce text, images, video and audio. Correctness becomes coherence, originality, plausibility and adherence to domain rules, and the number of possible inputs grows enormously.

The input explosion problem why it is hard

There is an optional system prompt and a user prompt, each able to carry large and varied data. There is an API as well as a UI. Parameters such as temperature and maximum tokens change the output, and the context window keeps earlier turns active and influencing everything after them.

ConsequenceYou cannot enumerate the input space. Sample it deliberately and record the parameters with every result, or the result is not reproducible.

Benchmarks standardised

Curated datasets and tasks that allow consistent comparison of models in language understanding, reasoning and coding. They are systematic and reproducible, unlike ad hoc prompting.

Use it forwhether the new model version is better than the current one, and not for checking whether a feature is correct.

A second model as judge automation

Manual review is often unavoidable, and pass or fail then depends on qualitative criteria that must be written into the requirements. Where it can be automated, a second generative AI system determines the result, for example an image recognition system checking a generated image.

CarefulThe judge can reproduce the same biases and the same errors as the system it judges.

Red teaming fault attack

Deliberately pushing the system to produce harmful or undesirable output such as privacy violations, hateful content or dangerous instructions. The findings are used to strengthen the system. It is usually black-box and end-to-end, and increasingly expected by regulation such as the EU AI Act.

The core activity is interactive prompting over many turns, typically 15 to 20. The cycle is: 1) assemble a diverse team to cover many perspectives and attack vectors 2) give it access in a safe test environment 3) probe, open-ended or by checklist 4) analyse the failures to understand the threats 5) turn them into datasets that drive mitigations.

ScopeNot only security. It also covers reliability, privacy, fairness, bias and misinformation, and for safety the focus is often harmful output under ordinary use, with no attacker at all.
Coverage at scaleCrowd-sourced prompt generation, or one LLM generating attack prompts while another checks the outputs. Hybrid works best: human creativity, machine scale.

Red vs blue before vs during

Red teaming is proactive and takes place before deployment, ideally after internal quality checks and before release. Blue teaming is the running defence: ongoing real-time monitoring and filtering of live input. What red teaming finds is what blue teaming should then watch for.

Security specificsIndirect prompt injection, and malicious content hidden in documents the RAG retrieves.

Non-functional, same as ever

Resource utilisation during inference and training, because it is a direct cost: CPU and GPU usage, memory consumption, network bandwidth, response times.

ExampleAnswer quality is fine; the per-request cost makes the feature unshippable.

7Deployment and the watch afterwards

An ML system is released into an environment that keeps changing. These checks exist because working in training is not a release criterion.

Install & uninstall

Install, upgrade and uninstall cleanly in every supported environment, including system dependencies such as GPU drivers, framework compatibility and the installation scripts.

ExampleWorks on the dev box, fails on the edge device with the older driver.

Rollback test it first

Restore the previous working state after a degraded or failed deployment, either for the model only or for the whole system including the data pipeline. It has to be exercised before deployment; a rollback first attempted during an incident is not a rollback.

ExampleNew model ships, accuracy drops, previous version is back in minutes.

Canary release a slice of real users

Release to a small share of production traffic, for example 5 % of users, and watch real-time metrics such as latency, accuracy and error rate to detect regressions before the full rollout.

Example5 % of users on v2 for a day; error rate doubles; the rollout stops there.

Shadow testing zero user risk

Route the same requests to both the new and the current system, without affecting the live responses. It compares old and new on live data in a controlled, low-risk setting, and uncovers performance regressions and data drift before full deployment.

ExampleTwo weeks of shadow traffic show the new model is better overall but worse on one customer segment.

Format conversion & portability

A model converted from its training format into a deployment format must keep consistent behaviour and acceptable efficiency in inference speed and memory use. Confirm this on every target, from mobile and edge devices to cloud servers.

ExampleQuantising for mobile costs 4 points of accuracy. Once this is known, it becomes a release decision.

Monitoring is the test that never ends

Drift testing from section 5 belongs here, with a static distribution comparison in every case and a dynamic comparison against user feedback where ground truth exists. Add API testing of inputs, outputs, error messages and the integrations around the model, such as data feeds, clients and the pipeline.

Keep in mindFor an adaptive system, monitoring is the regression suite, because the behaviour approved today will not be the behaviour next month.
◆Development-side risks worth a review rather than a test: sub-optimal algorithm or framework choice · wrong hyperparameters · defective allocation of data to the training, validation and test sets · a weak evaluation approach such as skipping k-fold cross-validation · non-reproducible results from the stochastic nature of learning · framework security vulnerabilities and poor framework documentation.

8The opposite direction: testing with GenAI

CT-GenAI covers the opposite case: the product is ordinary, and the LLM is your tool. The tool is confidently wrong sometimes, so its output is itself a test object.

Three failure modes know the difference

Hallucination, meaning factually wrong or irrelevant output such as fictitious test cases, scripts that do not run or tests for acceptance criteria that do not exist. Reasoning error, meaning misread conditional logic, cause and effect or step by step problem solving. LLMs match patterns rather than reason, so test planning, estimation and prioritisation are most affected. Bias, inherited from training data and visible in generated test data and in rewritten acceptance criteria.

ExampleThe model generates a beautiful test suite for a field the spec never mentions.

Detecting them

Hallucination: cross-check against the test basis and known system behaviour, which can be automated against trusted sources, and use expert review and consistency checks across several answers. Reasoning: review the chain of reasoning for coherence and run the generated testware against the real test object, which settles the question. Bias: check what the output over- and under-represents relative to the test strategy.

How much of thisScale it to the estimated risk of the task. Generated smoke tests ≠ generated safety-critical tests.

Mitigating them

Give full context in the prompt · split the work into steps with prompt chaining and verify each output before moving to the next · use structured, straightforward input formats · ground the model in your own documents with RAG · and cross-check by running the same task on several models and comparing the outputs.

Non-determinismLower the temperature, which narrows the probability distribution at the cost of variety, and fix the random seed. Neither guarantees full reproducibility, so automate the verification instead of relying on identical reruns.

Evaluate, then refine the loop

Judge GenAI output on accuracy against expert-written tests or the requirements, precision, recall, which checks whether the generated cases cover the valid and invalid partitions, relevance and contextual fit to the test basis, diversity of behaviours and edge cases, execution success rate, which checks whether the scripts run at all, and time efficiency versus doing it by hand.

Then refine the prompt: improve wording and context, compare two prompt versions against those metrics, analyse recurring error types, ask the testers who use the output, and try both longer and shorter prompts, because more context does not always help. Share what works in a prompt library.

Because output variesThe metrics have to be computed over a statistically relevant sample, not over one impressive answer.

RAG and agents the infrastructure

RAG splits your documents into chunks of roughly 256 to 512 tokens, stores them in a vector database, retrieves the closest chunks for each query and gives them to the model as context. This grounds the answers in the current specification instead of the training data. LLM-powered agents go further. They call predefined functions, called tools, and act on external systems with partial or full autonomy, sometimes with several agents working together.

Keep in mindAgents inherit every failure mode above, and now they act on it. Automated verification of their results, or semi-autonomous mode for anything critical.

Privacy, and shadow AI policy, not technique

Test data and specifications pasted into a public model may be stored, reused for training or exposed. This is a GDPR problem as much as a security problem. Shadow AI, meaning staff using unapproved tools on their own, turns this into uncontrolled data leakage, compliance exposure and intellectual property disputes.

The fix is organisationalAn agreed strategy, approved tools, and clear rules about what may be pasted where.

The logic is the same as on the manual testing page. Start from what is missing, whether the oracle, the data or the stability, and the technique follows.

The test process in seven activities

This page is pure theory: not which system to test, but how the work of testing is structured, whatever the system. Every project performs some version of these seven activities. They are not a waterfall. Analysis, design, implementation and execution overlap and repeat in every iteration, while monitoring and control runs alongside all of them from start to finish. The map below follows the cycle in order. The sections after it describe one activity at a time and end with work products, traceability, the two testing roles and the strategy choices that shape planning.

1Test planning

Defines the objectives of testing, then picks the approach that reaches them most effectively within the constraints of the context. It is revisited whenever the plan drifts from reality, not written once and filed away.

What a test plan documents ISO, IEC and IEEE 29119-3

Scope, objectives and test basis, assumptions and constraints, stakeholders with their roles, needs and training, how and how often information is communicated, the risk register, the approach including levels, types, techniques, work products, entry and exit criteria, independence, metrics, data and environment needs, and finally the budget and schedule.

Entry & exit criteria gatekeeping

Entry criteria require resources, testware and a basic level of quality, for example a passing smoke test, before a level starts. Exit criteria can be coverage reached, defects below an agreed density or a simple condition such as all planned tests having run. Running out of time or budget is also a valid exit criterion if stakeholders knowingly accept the remaining risk. In agile teams these are usually called the Definition of Ready for each story and the Definition of Done.

Four estimation techniques

Ratio-based estimation reuses the ratio of development to testing effort from past projects. Extrapolation measures the first iterations and projects the rest. Wideband Delphi and planning poker let experts estimate separately, compare and repeat until they agree. Three-point estimation uses an optimistic value a, a most likely value m and a pessimistic value b: E = (a + 4m + b)/6 with a standard deviation of (b − a)/6.

Prioritizing test cases

By risk, covering the biggest risks first, by coverage, maximising coverage or prioritising whatever adds the most new coverage, by requirement or business priority, or by history, running first whatever has failed most often.

Planning in iterative lifecycles

Release planning shapes the product backlog and the approach for every following iteration: testable user stories, acceptance criteria, input on project and product risks, and an effort estimate for the release. Iteration planning works one backlog at a time: detailed risk analysis per story, testability, splitting stories into tasks and estimating each one.

◆A test plan does not create its approach from nothing. A mature organisation relies on an existing test policy and test strategy. See section 9.

2Test monitoring and control

Two linked activities that run continuously from planning to completion. They are not a stage that is passed only once.

Monitoring vs. control

Monitoring is the ongoing comparison of actual testing against the plan. Control means acting on that information by issuing directives that keep testing on track for its objectives.

What gets measured

Project progress, such as tasks completed and effort spent. Test progress, such as cases implemented, run, passed and failed, and environment readiness. Product quality, such as availability, response time and time between failures. Defects, such as the number and priority of defects found and fixed, defect density and detection rate. Remaining risk, coverage of requirements and code, and the cost of testing itself.

Test progress report recurring

Issued regularly, for example daily or weekly. It covers the period, progress against the schedule, deviations, obstacles and how they were handled, the metrics above, new or changed risks and the plan for the next period.

Test summary report at completion

Written once, at a milestone: a summary of testing, a quality assessment against the original objectives and exit criteria, deviations from the plan, impediments met, the metrics gathered, unmitigated risks and open defects, and lessons learned.

Typical control actions

Changing test priorities when a risk occurs, checking entry and exit criteria again after a fix, rescheduling because the environment was delayed and adding resources when needed.

3Test analysis: what to test

Turns the test basis into a prioritized list of testable conditions, before a single test case gets written.

From test basis to test conditions

Analyse the test basis to find testable features, then define and prioritise the test conditions for each one according to the risk and risk level they relate to.

Defects found before a test exists

Reading the test basis closely often reveals ambiguous, missing or contradictory requirements. These are reported like any other defect, because analysis already finds defects and is more than preparation.

Testability

Is the item specified clearly and completely enough to test? Is it accessible and controllable through hooks, logs and observable outputs, or is it a black box with nothing to check against?

Where test techniques come in

Black-box, white-box and experience-based techniques, described on the Manual testing page, are the tools of analysis, so conditions come from a systematic method rather than guesswork.

Measurable, not vague

Conditions are written so that they can be counted later. Every documented error message being produced at least once is testable. Good error handling is not.

4Test design: how to test

Converts each test condition into one or more concrete test cases, plus everything the cases will need in order to run.

Conditions become cases

Each condition becomes one or more test cases, or test charters for an exploratory session, guided by coverage items that determine exactly which inputs to choose.

Anatomy of a test case

An identifier, preconditions, the input or action, the expected result and any postconditions. A good case can be traced back to the conditions it was built to cover.

Test data requirements

The values, records and combinations the cases need are decided here and built later during implementation.

Test environment design

Hardware, network, stubs, drivers, simulators, virtualized services and any other tool or infrastructure piece the cases will depend on.

◆Design is still based on the specification. It does not decide who will run the case. Manual vs. automated is a choice made afterward, in implementation.

5Test implementation

Builds or obtains everything the test cases need to run. At this point testware stops being a description and becomes executable.

Procedures & suites

Test cases are arranged into test procedures, also called scripts, and then grouped into test suites for efficient execution.

Scheduling execution

Procedures are prioritized and arranged into a test execution schedule, so the cases that matter most run first regardless of what happens to the rest of the run.

Scripting

Manual scripts are written for a person to follow step by step. Automated scripts are written for the chosen framework, as described on the Automated testing page.

Building the environment

The test environment is assembled and verified to be correctly configured before the first test runs against it, instead of being found to be wrong afterwards.

Traceability check

Implementation is also where the link in both directions between test basis, conditions, cases and scripts is verified rather than assumed.

6Test execution

Running the tests per the schedule, manually or with a tool, and reacting to whatever comes back.

Forms it takes

A scheduled test run, continuous testing in a pipeline or a paired exploratory session. The activity is the same, only the frequency differs.

Comparing & logging

Actual results are compared with expected results, and every run is logged with what ran, the build or version used and whether it passed or failed.

From anomaly to defect report

A failure is analysed for its likely cause before it gets reported, so the report already points roughly at where the problem lives rather than just describing the symptom.

Confirmation & regression

A confirmation test checks that a specific fix worked. Regression testing runs other tests again to check that nothing else was broken.

7Test completion

Closes out a chunk of testing at a milestone and turns it into knowledge the next cycle can reuse, instead of letting it evaporate.

When it happens

A test level finishes, an agile iteration ends, the project ends or is cancelled, or a maintenance release ships.

What gets checked

Every open defect report, change request and backlog item from the finished testing is accounted for. It is closed, postponed or deliberately carried forward, and never silently dropped.

What gets kept

Testware worth reusing is identified and archived, or handed over to whoever maintains it next; the test environment is shut down in an agreed, reproducible state.

What gets written

A test summary report for stakeholders as described in section 2, and a short retrospective on what worked and what should change next time.

8Work products, traceability and the two roles

Every activity above leaves something behind, and all of it should trace back to the test basis it came from.

Work products, by activity

Planning: test plan, schedule, risk register, entry and exit criteria. Monitoring & control: progress reports, control directives, risk updates. Analysis: prioritized test conditions, defects against the test basis. Design: prioritized test cases, test charters, coverage items, data and environment requirements. Implementation: test procedures, scripts, suites, data, environment components. Execution: test logs, defect reports. Completion: test summary report, lessons learned, change requests.

Why traceability matters

Linking the test basis to conditions, cases, results and defects allows you to prove coverage, assess the impact of a change, support an audit and turn a figure such as 70% code coverage into something stakeholders can act on.

Two roles, not two people

A test management role owns planning, monitoring, control and completion. A testing role owns analysis, design, implementation and execution. One person often holds both; in agile the team usually absorbs the first role, and only cross-team concerns go to a test manager outside it.

9Test strategy behind planning

Advanced-level material. A test strategy is the organization's general, reusable approach to testing; a test plan is what one project does with it. Real strategies are usually a blend of several of these, not a single pure choice.

Analytical e.g. risk-based

Conditions are derived from analysing the test basis, such as risks and requirements, instead of being decided in advance.

Model-based

Build a model of the real or expected environment, inputs and behaviour, such as an operational profile for performance testing, and test against that model.

Methodical

An agreed checklist or quality standard, such as the ISO 25010 characteristics, applied the same way in every release.

Process- or standard-compliant

Follow a process required from outside the test team, for example by a regulator or by the ceremonies of a framework such as acceptance criteria in each Scrum iteration, instead of a process designed by the team.

Reactive

Design and run tests only once the software exists, reacting to its actual behaviour. The natural home of exploratory and attack-based testing.

Consultative

Test conditions come mainly from a key stakeholder, for example a prioritised matrix of browsers and operating systems given to an external test supplier.

Regression-averse

Heavy automation aimed specifically at the risk of regression, re-run on every change.

◆A test strategy also states the levels it applies to and their entry and exit criteria. It can cover integration order, independence, environments, automation, tools, reuse, retesting and regression, reporting, metrics, defect management, configuration management and roles, all consistent with the test policy of the organisation.

Automated testing and how a suite should be built

Writing a script that clicks or calls something is the easy part. What decides whether a suite is still trusted a year later is its structure: which tests are automated at which level, how the code is layered, what one test looks like inside, who owns the state it leaves behind, and how it waits for a system that answers asynchronously. A suite that fails at random, or passes while the product is broken, is worse than no suite. Every box below is clickable.

1Why automate, and what automation is not

Automation does not find new defects by itself. It re-checks, cheaply and quickly, things somebody already decided are worth checking.

What it buys you the point

Fast and repeatable regression testing on every change, checks a person cannot do well such as thousands of combinations, exact numbers and timing, and a living specification, because a readable test states what the system is supposed to do.

ExampleAfter every hedger deploy, the same exposure scenarios run in minutes and give the same verdict for the same build.

What it does not replace limits

Exploratory testing, usability, judging whether a requirement makes sense and anything whose expected result nobody can write down. An automated test only checks what it was told to check and misses everything around it.

Keep in mindA passing suite means that the written checks still pass, not that the product works.

Automation is software treat it so

A test suite has its own code, architecture, reviews, defects and technical debt. It deserves the same standards as production code: version control, review, naming, no copy-paste, refactoring.

Rule of thumbIf nobody would accept the code in the product, it should not be accepted in the tests either.

Trust is the product the real metric

A test is useful only if a failure reliably means that something is broken and a pass reliably means that the behaviour still works. False alarms teach people to ignore failures, and false passes hide them.

ExampleOne test that fails every third run for no reason makes the whole team rerun the pipeline instead of reading the failure.

2Strategy: what to automate and at which level

The cheapest test that can catch a defect is the right place for it. Push checks down to the lowest level that still sees the behaviour.

The test pyramid shape of a suite

Many fast unit tests at the bottom, fewer service and API tests in the middle, a thin layer of end-to-end tests on top. Lower tests are faster, more precise about where the defect is, and less brittle; higher tests prove the parts work together.

Anti-patternThe ice cream cone: mostly end-to-end UI tests and almost no unit tests, which is slow, unstable and unclear about the cause of a failure.

What each level is for the layers

Unit: one function or class, no network, a few milliseconds. Integration and contract: two components and the agreement between them, such as the shape of requests and responses. API and service: a deployed service tested through its real interface. End-to-end: a user flow across several services.

In our suiteThe hedger tests are service-level: real PLAT and CORE gateways on test-env, no UI. That is the right level for exposure and routing rules.

Choosing what to automate selection

Automate what is run often, is stable, is risky if it breaks, has a clear expected result and is tedious or error-prone by hand. Leave out one-off checks, features still changing every week, and anything whose oracle is a human opinion.

Rule of thumbEvery regression bug that reached production is a candidate for a test at the lowest level that would have caught it.

Return on investment cost is ongoing

The cost of a test is not in writing it but in running, debugging and updating it for as long as it exists. A test pays off when the number of runs multiplied by the manual effort saved exceeds the cost of building and maintaining it and the time lost to false failures.

ExampleA brittle UI test rewritten after every redesign can cost more than doing the check by hand.

3Architecture: layers, so that a change affects one place

The test says what is checked; lower layers know how to communicate with the system. When an endpoint changes, one helper changes instead of forty tests.

The generic test automation architecture ISTQB TAE

Four layers: test generation, where cases come from, whether written by hand or generated from models or data, test definition, the test cases and their data, test execution, covering the runner, setup, logging and reporting, and test adaptation, the code that communicates with the system under test.

Why it mattersEach layer can change without rewriting the others: a new runner, a new API version, new data.

Adaptation layer clients & helpers

API clients, page objects or protocol helpers hide URLs, authentication, payload shapes and parsing. Helpers are named after the business action, such asopen_market_order, enable_all_assignments, and not after the HTTP call.

In our suiteutils/http.py handles transport and tokens, utils/methods/*_utils.py contains business actions and tests/… contains scenarios only.

Configuration out of code one place

Environment URLs, accounts, symbols and timeouts live in configuration, not scattered through tests. Secrets never sit in the repository. The same suite must run against another environment by changing configuration only.

In our suiteutils/config.py plus the mcp-server vault for tokens; tests never contain a password.

Scripting approaches how tests are written

Linear, recorded and copied steps, then structured, shared functions, then data-driven, one script with many data rows, then keyword-driven, tests composed from business keywords, and finally model-based, cases generated from a model. Higher approaches cost more to start and much less to maintain.

Example@pytest.mark.parametrize over volumes and sides is data-driven: one test body, every row reported separately.

4Anatomy of one good test

Someone who has never seen the test should understand from its name and body what is checked, and from its failure message what went wrong.

Arrange, Act, Assert three blocks

Arrange the preconditions, act once, which is the behaviour under test, and assert on the outcome. Given, When, Then is the same idea in business language. Mixing the blocks, for example asserting, acting again and asserting, usually means two tests in one.

ExampleArrange: rule on, account 1004 disabled. Act: client 1001 buys 30 lots SYMBOL1. Assert: 1004 received no order, the others got the split.

One behaviour per test focus

A test checks one rule, so a failure points to one cause. The name states the rule and the expected outcome, for example test_disabled_hedger_gets_no_share, not test_hedger_3. Several assertions are fine when they describe the same outcome.

SmellA test called full flow that fails on step 7 of 12 tells you nothing until someone reads the log.

Assertions that explain the failure is the report

Assert on exact expected values derived from the specification, not just on the fact that something was returned. Include the context in the message: expected value, actual value, the account and the step. Never assert on a value the test calculated in the same way as the product.

Exampleassert vol == 6, f"1002 should hedge 6 lots, got {vol}" beats a bare assert vol.

FIRST properties to check

Fast enough to run often, Independent of other tests and their order, Repeatable in any environment and on any run, Self-validating, with a clear pass or fail and no need to read logs, and Timely, written together with the change and not months later.

CheckRun the suite in random order and twice in a row. Anything that changes the verdict breaks I or R.

5State and data: the test owns what it changes

Most unstable suites are not unstable because of timing but because tests share state: an account, a rule, an open position left by the previous test.

Fixtures setup in one place

The known state a test starts from, built by shared and named fixtures instead of copied setup. The scope is chosen deliberately: per test for anything the test changes, and per module or session only for expensive read-only items such as a login token or a downloaded instrument list.

In our suiteautotest_rule in tests/hedger/conftest.py prepares the AUTOTEST hedge rule for each test.

Teardown that always runs leave it clean

Restore what was changed in a yield fixture or finally, so it runs even when the assertion fails. Then verify the clean state instead of assuming it, because the next test depends on it.

In our suiteExposure is zeroed only after the rule is on and every matrix account is isEnabled=true, then the state is read back to confirm it is 0.

Test data known, owned, unique

Data created by a test should be unique, for example ids, order ids and names with a run suffix, so that parallel or repeated runs do not collide. Shared environment data is read rather than assumed, and shared resources are reserved for automation or locked while a suite runs.

Rule of thumbNever let a test depend on data another test created. Builders or factory helpers make the needed data explicit.

Test doubles Meszaros

Dummy, filler that is never used, stub, which returns prepared answers, spy, which records calls, mock, which expects specific calls, and fake, a working lightweight implementation such as an in-memory FIX acceptor. They make lower-level tests fast and deterministic, while service-level tests use the real system.

In this appThe FIX client tests run against a fake acceptor on the local machine, so logon, orders and logout are checked without the test environment.

6Reliability: waiting, retries and unstable tests

An unstable test passes and fails on the same code. It is a defect in the test, the environment or the product, and never background noise.

Wait for a condition, not for time no sleep

Asynchronous systems need waiting, but a fixed sleep(5) is either too short, which makes the test unstable, or too long, which makes it slow. Poll for the expected state with a timeout and a clear message when it never arrives.

ExampleCheck positions every 0.5 s for up to 10 s until account 1002 shows 6 lots, instead of waiting 10 s and reading once.

Retries are not fixes be honest

Retrying a check that races with eventual consistency is legitimate. Re-running a whole failed test until it passes hides the defect. If a test needs a rerun to pass, that is a finding, not a pass.

In our suiteutils/retry.py repeats a verification step only on AssertionError, and its documentation states that a test which needs it in order to pass belongs in the bug registry.

Quarantine, then fix contain it

A known unstable test is removed from the gating run with a ticket and an owner, so that people do not learn to ignore failed builds, and it returns once fixed. Typical causes are shared state, order dependence, timing, test data collisions and an unstable environment.

Rule of thumbQuarantine with a deadline. A quarantine nobody looks at is deleted coverage.

The environment is part of the test shared ground

Service-level suites run on a shared environment. Two suites changing the same rule at once will both fail for reasons neither caused. Serialise runs that share resources, and check the environment is healthy before blaming the product.

In our suiteOnly one pytest run at a time on the test environment, and an unreachable environment is reported as unverified rather than as failed tests.

7Running the suite: pipeline, tags and reports

A suite nobody runs automatically decays. Wire it into the delivery pipeline, and make its output usable by someone who did not write it.

In the pipeline continuous

Fast checks on every commit, the service-level suite on every deployment to the test environment and long or costly suites every night. A failure blocks the change it belongs to, so feedback arrives within minutes and not a week later.

Rule of thumbThe longer the gap between the change and the failure, the more expensive it is to find the cause.

Tags and selection run what you need

Markers group tests by area, risk or cost so a run can be selected: smoke only, everything touching trading, one service. Strict markers stop a typo from silently creating a new, empty group.

In our suitepytest.ini defines PLAT, CORE, ADMIN, MANAGER, TRADING and SMOKE with --strict-markers.

Reports with evidence traceable

A useful report states which behaviour failed, on which build and environment, with the requests, responses and values that prove it, and links the test to the requirement or ticket it covers.

In our suiteutils/scenario.py attaches the scenario to the report, so a failure reads as a test case, not only as a stack trace.

Maintenance continuous, not a project

Review tests like code; delete tests that no longer check anything meaningful; refactor helpers when the same steps appear in several tests; track the suite's run time and flaky rate as health metrics.

SmellA test nobody understands but nobody dares delete. Either document why it exists or remove it.

8Test smells: signs of a wrong structure

Each smell has a structural cause. Fixing the cause fixes every test that shows it.

SmellWhat you seeStructural fix
Fragile testBreaks on changes unrelated to what it checksMove endpoint and payload details into the adaptation layer
Unstable testSame code, different verdictsIsolate state, poll instead of sleep, unique test data
Interacting testsPasses alone but fails in the suite, or the other way roundPer-test fixtures with guaranteed teardown and a verified clean state
Obscure testYou cannot tell what is checked without reading helpersBusiness-named helpers, Arrange-Act-Assert, a name that states the rule
Assertion rouletteMany bare asserts, so a failure only says AssertionErrorAssertion messages with expected, actual and context
Conditional test logicif / try deciding what to assertSplit into tests with fixed preconditions; a test has one path
Test code duplicationThe same ten setup lines in every fileFixtures and helpers; data-driven parametrisation
Slow suiteNobody runs it before pushingPush checks down the pyramid; wait for conditions; run in parallel where state allows
Green but blindPasses while the feature is brokenAssert on exact expected values from the spec; see a test fail before trusting it

9How to choose

Same logic as the other pages: start from the problem you have, and the structural answer follows.

SituationReach forWhy
A business rule with clear inputs and outputsUnit or service-level test, data-drivenCheapest level that still sees the rule; one body, many rows.
Two services must agree on a messageContract testCatches a broken agreement without a full end-to-end environment.
A user flow across several systemsA few end-to-end testsProves the integration; keep them few, the detail lives lower down.
The system answers asynchronouslyPolling with a timeoutWaits exactly as long as needed and fails with a reason.
Tests fail only when run togetherPer-test fixtures, verified teardownThe cause is shared state, not the assertion.
An endpoint change broke forty testsAdaptation layer and helpersThe next change touches one function.
A dependency is slow, costly or unavailableTest double, such as a stub or a fakeDeterministic and fast; keep a few tests against the real one.
A test fails at randomQuarantine with an owner, then root causeProtects trust in a red build while it is fixed.
A production bug escapedRegression test at the lowest level that catches itTurns the incident into a permanent check.
◆Three things worth memorising. First, a suite is only as valuable as the trust people have in it, and one unstable test costs more than it finds. Second, structure matters more than volume, because layers and fixtures determine the maintenance cost of every future test. Third, never trust a test you have not seen fail.
◆Test design comes first. Automation executes test cases; it does not choose them. Equivalence partitioning, boundary values and decision tables from the Manual testing tab decide which cases are worth automating.
